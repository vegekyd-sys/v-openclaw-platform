# 老板上手与交付后头几天

给去客户现场部署 V 的人（或 V 自己）看。安装、配置、建飞书应用、升级回滚见 [`distro/DEPLOY.md`](../DEPLOY.md)；这里从「机器装好、飞书机器人在线」开始，到交付后第一周。

文中的命令都在工作区根目录、以服务用户（agent 的环境）执行，怎么进入这个环境见 DEPLOY.md。命令只给部署者自己看，**不要把命令、文件名、权限英文名说给老板听**。

## 0. 开始之前

- DEPLOY.md 的安装和飞书接入都做完，健康检查通过。
- 飞书应用的用户身份权限按 [`feishu-user-scopes.txt`](feishu-user-scopes.txt) 开通，并且应用已经发布了新版本。没开的权限上手时不会申请，之后用到那一类就要老板再点一次补授权。
- 老板本人在场，手机上登着自己的飞书。

## 1. 记下主人

这台 V 只服务一位主人。两种方式，二选一：

| 方式 | 怎么做 | 注意 |
|---|---|---|
| 安装时填老板的 open_id | DEPLOY.md 里的 `V_OWNER_FEISHU_OPEN_ID` | 只有老板的私聊和老板在群里说的话能进来，最稳 |
| 安装时不填，用配对码 | 老板第一次私聊机器人会收到配对码，部署者按 DEPLOY.md 批准 | **一定让老板本人第一个私聊**，别让同事先试 |

老板第一次私聊时，V 会把他记成主人（工作区 `onboarding/owner.json`）。核对：

```bash
python3 scripts/v-schedule.py owner      # 打印主人的 open_id；没有记录时退出码 1
```

记错了人（例如同事先发了消息）：这不能在聊天里改，按 DEPLOY.md 重新配置主人后再开始。

## 2. 授权链接

老板第一次私聊 V（随便说什么都行），V 先回一段开场白，接着发**飞书授权链接和二维码**。

- 老板用自己的飞书点链接，在页面上按**「确认授权」**，然后回 V「好了」。
- 链接 **10 分钟有效**。过期了就让老板跟 V 说「重新发一下授权」。
- 这一次就申请了应用上开通的全部用户权限（飞书一次最多约 250 项，V 的那些排在前面），以后建文档、日程、任务、多维表、表格、发消息都不用再一项项点。
- 企业要管理员审批的：V 会改发一个「开通权限」的链接（`grant`），让管理员批完再回「好了」。

核对是否授权成功：

```bash
python3 scripts/feishu-docs.py status    # authorized 为 true
lark-cli auth status                     # identities.user.status 为 ready，scope 数和应用开通的接近
```

常见问题：

| 现象 | 原因 | 处理 |
|---|---|---|
| 老板说点了，V 还在等 | 点的是旧链接，或者打开了没按「确认授权」 | 让 V 重新发，当场看着老板点「确认」 |
| 授权页报权限太多 | 应用开通的用户权限超过一次授权的上限 | 脚本会自动截到上限内；还报错就把 `scopes` 的输出发回给 Tianyi |
| 上手后做某件事时又要补授权 | 应用上那一项当时没开 | 在开放平台给应用补开、发版，再让 V 补授权 |
| 升级或重新配置后 V 读不到飞书了 | 老版本安装器会清掉登录（已修，见 DEPLOY.md） | `lark-cli auth status` 看是否 missing，是就让老板重新授权一次 |

不要让老板把密码、验证码、key 发到聊天里，也不要替老板点授权。

## 3. 上手引导每一步老板会看到什么

整个引导大约 15–30 分钟（取决于飞书文档多少），V 每条消息都以「下一步要你做的那一件事」结尾。

| 步骤 | 老板看到的 | 老板要做的 | 卡住时 |
|---|---|---|---|
| 0 开场 | 「我是 V，你的专属助手……」＋授权链接和二维码 | 点链接、确认、回「好了」 | 见上一节 |
| 1 等授权 | 没有新消息，直到他回「好了」 | — | V 不追问；老板回来时从这里接着 |
| 2 读文档 | 「我在读你的文档……」，几分钟内说读了哪些空间、多少份 | 无 | 超过 5 分钟没消息：V 会说「我在后台接着做」，过几分钟发结果 |
| 3 初稿 | 一份「我对你的理解」：你是谁、公司在做什么、手上的事（飞书文档链接） | 看一遍，哪里不对直接说 | 老板没空：说「先放着」就行，V 下次接着 |
| 4 纠正 | V 按老板说的改，再问一次有没有要补的 | 改到满意，或说「可以了」 | — |
| 5 再多了解一点 | 依次问：官网网址、别的 AI 助手里的记忆、其它资料 | 每项都可以回「跳过」 | 不想给的直接跳过，V 不劝 |
| 6 收尾 | 报账：接进来多少份、大约多少字、还要几个晚上整理完；说明数据只在这台机器上；问要不要起名字 | 回一个名字或「不用」 | V 说「后台任务没登记上」：见下一节 |

最后一条是「好了，从现在开始有什么事直接跟我说。」看到这句，引导就结束了。核对：

```bash
python3 scripts/onboard-progress.py get  # step 是 done
python3 scripts/v-schedule.py list       # 9 条 distro: 开头的后台任务都在
```

## 4. 出问题怎么处理

| 现象 | 先看 | 处理 |
|---|---|---|
| V 完全不回 | DEPLOY.md 的健康检查和网关日志 | 按 DEPLOY.md 排查；不要在工作区里改配置 |
| 引导停在某一步 | `onboard-progress.py get` | 让老板随便发一句话，V 会从记的那一步接着；仍不动就看网关日志 |
| 后台任务没登记上 | `v-schedule.py list` | `python3 scripts/v-schedule.py install`；报「record the owner first」就先做第 1 节 |
| 文档读得很少 | `python3 scripts/feishu-docs.py scopes` | 缺读文档的权限：补开、发版、让 V 补授权；老板的文档大多在别人空间里的，让老板把空间分享给自己或机器人 |
| V 以老板的名义发了消息或评论 | 不应该发生：`lark-cli` 会拦下以主人身份发言（`V_OWNER_VOICE_BLOCKED`） | 截图发给 Tianyi；只有老板亲口要求「替我发」时才允许，并记审计 `~/.openclaw/audit/lark-owner-voice.log` |
| 出图没有 Makaron 任务卡片 | 环境里有没有 `MAKARON_API_KEY` | 没有就让老板提供 Makaron key，按 DEPLOY.md 写入 |
| 要网页或公网链接 | 环境里有没有 Vercel / Cloudflare 凭据 | 没有时 V 会直说「需要补账号」，先发文件，这是预期行为 |
| 夜班说「没开通」 | `nightshiftctl health` | 夜班服务按 DEPLOY.md 另装；没装就是预期行为 |

部署者自己不要用老板的飞书身份做任何事，也不要读老板的文档内容；排查只看状态和日志。

## 5. 交付后头几天

### 每天固定发生的（时间按老板时区）

| 时间 | 发生什么 | 老板会收到 |
|---|---|---|
| 20:30 | 重新盘点老板的飞书文档，新的、改过的进整理队列 | 只有授权失效时才收到一条重新授权的提醒 |
| 21:00 | 记忆整理：把读进来的资料编成 wiki（每晚最多 20 片） | 无 |
| 22:00 | 质检抽查当晚的整理 | 无 |
| 00:00 | 午夜报告：当天做了什么、卡在哪、明天最该做的 1–3 件事 | **每天零点一条私聊**（当天什么都没发生就不发） |
| 03:00 / 05:00 / 07:00 | 导入补编：整理队列还有剩就各再编最多 30 片 | 无 |
| 08:00 / 20:00 | 维护：反思、记忆扫描、wiki 维护 | 无 |
| 08:30 / 14:30 / 20:30（02:30 那轮在安静时间里不发） | 主动推进：从记忆里找一件现在对老板有用的事，查清、准备好再发 | 有才发，没有就不发；同一件事 24 小时内只提一次 |
| 12:00 | 主动推进的每日复盘：过去 24 小时的提醒哪些有用、哪些多余 | 前一天发过提醒才有 |
| 周日 20:00 | Skill 周复盘：哪些做法值得沉淀 | 一条短消息，没有素材就一句话 |

安静时间默认 23:00–08:00，这段时间主动推进不发消息。老板想改（例如改成 22:00–09:00、或者主动推进改成每周一次、或者关掉），直接跟 V 说。

### 整理要几个晚上

上手收尾时 V 会报一个数：还要几个晚上整理完。那是按每晚 20 片的保守算法（每片约 3500 字）；有凌晨三轮补编时通常快得多，一个晚上最多能编约 110 片。参考：一个中等规模的企业飞书（约 20 万字）大约 1–2 个晚上，很大的知识库会更久。想知道进度，老板直接问 V「整理到哪了」。

整理完之前 V 也能回答问题：没整理到的文档它会当场去读原文。

### 要提前告诉老板的

1. **每天零点会收到一条当天总结**，不想要可以跟 V 说关掉。
2. **刚开始的几天，主动推进的提醒可能不准或偏多**，中午那次复盘就是用来调的；觉得没用、太频繁，直接说，V 会改。
3. V 能替他读写飞书（建文档、日程、任务、表格），但**以他的名义给别人发消息之前会先问**；文档评论里的回复是机器人发的，不会显示成他本人。
4. 数据只在他们自己部署的这台机器上，可以随时让 V 导出或删除。
5. 需要他另外提供才能用的：Makaron key（出图出视频）、Vercel 或 Cloudflare 账号（网页和公网链接）、Apify key（社媒检索）、夜班服务（批量生产，另外部署）。没有时 V 会直说，不会假装做成了。
6. 有问题找谁：部署方的联系人和方式（现场写上）。

## 6. 现场验收（交付前过一遍）

- [ ] `v-schedule.py owner` 是老板本人。
- [ ] `feishu-docs.py status` 已授权；`lark-cli auth status` 用户身份 ready。
- [ ] 引导进度是 done，`v-schedule.py list` 有 9 条后台任务。
- [ ] 老板在私聊里让 V 建一个飞书文档、建一个日程，都不再要求补授权。
- [ ] 老板在一份文档上评论 @V，回复显示为机器人。
- [ ] （有 Makaron key 时）让 V 出一张图，看到任务卡片开出、进度更新、交付。
- [ ] 把以上结果写进给 Tianyi 的部署报告（见 V 的 `v-distro-deploy` 技能）。
