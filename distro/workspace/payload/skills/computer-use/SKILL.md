# Computer Use — 推到最后一厘米再交人

> 适用范围：任何「替 主人去操作网页 / 桌面 / App」的任务——下单、注册、充值、退票、填表、比价、读后台数据。
> 本 skill 与 `AGENTS.md` 的 Computer Use 条目配套：AGENTS.md 管判断，这里管流程。
> 单一真相源：停手条件、profile 选择、定位优先级、接管卡片格式，改动先改本文件。

## 触发条件

- 用户要求「帮我买 / 注册 / 充值 / 退掉 / 查一下后台 / 比价 / 填个表」
- 任务需要在浏览器或桌面里点、输、翻页、提交
- 用户说「你自己看着办，弄好了叫我」

## 第零步：选哪个浏览器

优先级：**V 自己的浏览器（browser 工具的默认 profile）> 主人授权给 V 的远程浏览器（装了 V Browser 一类的接入才有）> 云浏览器（替补，装机时配置了才有）**。前一个能做完，就不往后挪。

- 用主人本人已登录、而 V 的浏览器里没有的账号时，才借主人的浏览器；开工时说一句要借，只用借来的或自己新开的标签页
- 只有前一个浏览器被确定拦住（冷却重试后仍拦，或已知该站拦机房 IP）才往后挪；换之前在会话里说一句换到哪个、为什么
- 用付费云浏览器先说大概花多少钱；用完必须停掉
- 不管用哪个浏览器，付款都发支付宝二维码或确认链接给本人，见「付款怎么做」
- 某个站点在哪个浏览器能走通，试出结果后记进记忆，下次直接用

## 第一步永远是：确认 profile

**「一直停下来」最常见的根因不是不会做，是跑在一条空 profile 上。**

- V 的浏览器固定用一条**长期 profile**：登着 V 用来干活的账号（例如主人给 V 开的 Google 账号），不存主人的明文密码。Sign in with Google、收邮箱验证码都在这里做
- 浏览器的启动参数把 profile 固定住（例如 `browser.extraArgs` 里的 `--profile-directory=...`），不要靠浏览器记住上次用的是哪个
- 开跑前先验一下：打开 `accounts.google.com`，会跳到 `myaccount.google.com` 就说明在长期 profile 上；出现登录页或 profile 选择页，说明落错了 profile，先修好再做事，不要让主人重新登录
- 新任务一律新开标签页，不在当前标签上直接跳转（别的会话可能正在用）
- 不要另起干净环境，也不要把 V 接到主人自己日常用、存着密码的浏览器上，除非主人明确这样设置
- 交给主人接管时，卡片上写明是哪一个浏览器窗口

## 什么时候交给本人：按「谁做着容易」分工

不按「这一步危不危险」来分工，按「这一步谁做着容易」来分。V 做着容易的就自己做完，人做着容易、V 做着难的就立刻交出去。

**立刻交接**（`desktop_handoff_request`，主人直接接管 V 的浏览器）：
- 本人专属：硬件 2FA（手机 App）、输支付密码 / 卡号、实名认证（**登录密码和短信验证码不再交接**，用凭据卡代填，见「注册与登录」第 5、6 条；扫码付款见「付款怎么做」）
- **人一秒就能过、V 怎么都过不去的**：hCaptcha / reCAPTCHA / Cloudflare Turnstile、滑块、图形题、「按住不放」、Turnstile 一直转圈或 auto_timeout、站点要求的「新设备 / 异地登录确认」
- 人机验证**一出现就交接**。不要自己去解图形题、不要反复刷新重试，也不要先发「A 继续硬解 / B 换别的路」让人选。服务器出口多是机房 IP，这类验证会一直出题，解完 token 也是空的。交接卡上写明：哪个站、哪一个验证、过完之后 V 接着做什么

**自己做完、绝不停**：开站、登录（Google 一键登录）、填表注册（**注册 / 收货 / 联系 / 发票 / 公司资料都算**）、取邮箱验证码、搜索、比价、加购、进下单页、读数据。

反例：登录时 V 硬解了很久 hCaptcha，最后还是卡住；这一步交给本人，几秒钟就过了。反过来，注册表 V 能自己填完，却停下来等人，也是反例。

**邮箱验证码不算停手理由**——自己去收件箱取，见下节。

**卡住时不给二选一。** 只差本人一个动作，就发接管卡，只提这一件事；还有别的路，V 自己挑一条先做，做不通再换。不要发「1）… 2）… 你选」，日报里也不要把它列成「需要你决策」。

**填表不算停手理由。** 注册新站、开新户、走完整注册流程，这些字段全部由 V 填完；交回时用户只剩「验证 + 提交」一个动作，绝不是「填表 + 提交」。让用户去填一张空表是本 skill 的失败，不是谨慎。

停手前自问一句：**这一步真的只有本人能做吗？** 是 → 发接管卡片；不是 → 继续做。

## 取邮箱验证码

需要收信时，自己去开收件箱（同一个已登录 profile 里就是已登录状态），找最新一封相关邮件，读到码直接用。

- **码不进聊天、不进日志、不进 memory** —— 它属于凭据类内容，REDLINES 的 Credential Red Lines 管这个
- 邮件没到就等一轮（断言式等待 + 有上限重试），仍不行才发卡片
- 「新设备登录验证」「异地登录确认」这类邮件 -> 是风控信号，停手发卡片，不要自己确认

## 注册与登录怎么做

原则：登录和注册由 V 尽量全部做完，接管电脑是最后手段。按下面顺序试，前一种走不通才往下：

1. **站点支持就用 Sign in with Google**：profile 已登 Google 时是一到两次点击，零密码，最干净
2. **其次走浏览器已存密码的 autofill**：V 只触发填充，不读取、不记录明文
3. **扫码登录**：截出登录二维码（裁到只剩码、放大）用 `message send` 发到当前会话，请本人用对应 App 扫。发完**同一轮里自己盯着登录页**（短间隔 `wait textGone`，单次 ≤25s，长等待会断连），登上就直接往下做；码过期就点页面上的「刷新」再发一张。不要停下等用户回「好了」（2026-10-06 就因此空等了 20 分钟）
4. **邮箱验证码**（含 Google 登录时的验证码）：自己去 Gmail 收件箱取，见上节
5. **短信验证码 / 登录密码：用凭据卡代填，不发接管卡片**。V 先把其余字段填好（手机号、账号，短信码要先点「发送验证码」），然后：
   - 用 `secrets` 工具 `action=request` 发凭据卡：名字以 `LOGIN_` 开头（`LOGIN_<站点>_CODE` / `LOGIN_<站点>_PASSWORD`），`allowedHosts` 填登录页的确切域名，`reason` 写清是谁的账号、哪个网站。卡片发在当前会话里，**会话里谁填都可以**（同事登录自己的账号也这样做）；值不进聊天和会话记录
   - 卡片保存后重新 snapshot，用 `browser_fill_secret`（name + 输入框 ref + targetId）代填，再点登录 / 提交。值只会填进允许域名上的页面，填完即删
   - 被拒（如「密码错误」）就重新发一张卡说明原因，**不要猜、不要重试同一个值**；码过期就重新点发送再发卡
   - 永远不在聊天里要密码或验证码，不读回、不为核对去截图
6. 以上都走不通（人机验证、风控 / 新设备确认、硬件 2FA）才发接管卡片
7. 注册新站：填完所有非敏感字段（邮箱/姓名/电话/地址/公司）→ 触发并自取邮箱验证码 → 只剩人机验证或付款时才交出去。邮箱：V 自己的账号用装机时给 V 配的邮箱（密钥按 TOOLS.md「凭据存放与读取规则」读，只在同一个命令里用，不打印）；替主人注册用主人的邮箱；都没有就问主人用哪个
8. **建号成功要报一句**：站名 + 用的哪种方式（Google / 密码 / 扫码）+ 绑定邮箱。建号不可逆，事后报备是底线

## 付款怎么做

目标是走完最后一步，不是停在确认页。主人明确要求付款时：

1. 下单确认页核对好商品、规格、数量、地址、实付金额，点「立即支付」进收银台，记下地址栏里的收银台链接（`cashier*.alipay.com/...orderId=...`）
   - 确认页有「免密支付」选项时可以直接用，点下去就扣款、不用本人确认
2. **装了支付宝 AI 付（`alipay-payment-skill`）就首选它**：按该 skill 跑 `check-wallet` → `submit-payment --payment-link <收银台链接> --session-id <当前会话 UUID> --intent-summary "服务内容：…，支付金额：¥…，支付对象：…"`
   - 返回「支付待确认」时，把输出里的确认链接（`https://u.alipay.cn/...`）**作为可点击文字发到飞书，放在最前面**：「手机上点这个链接唤起支付宝确认：<链接>」。他在飞书里点一下就能付，不用切去支付宝扫码；确认码图片放在后面作备用
   - 同一轮里每 20 秒跑一次 `query-payment-status -p <u.alipay.cn 链接>`，到「支付已完成」后读淘宝付款成功页的订单号，回报结果
   - `submit-payment` 会输出很大的终端二维码，不要用 `tail` 截断，用 `grep -v $'\e\[4'` 过滤，状态文字要完整拿到
3. 没装或不可用时走**收银台扫码付款**：发码到会话，写明商户和金额；同一轮盯着页面，跳到 `pay_success` 就回报
   - 码过期不重下单：订单仍在「待支付」时从「继续支付 → 立即支付 → 支付宝 → 去支付」重走收银台即出新码；点「扫一扫付款」后用 `canvas.toDataURL()` 取原图放大 3–4 倍（别截图，会糊掉纠错区），发码时报较短的那个倒计时
4. 支付密码、银行卡号、短信付款码 V 一律不碰；只剩这类才发接管卡片

实测：扫码约 1 分钟付完；`open` 报 Target closed 时页面已开，等 2–5 秒再 `tabs`。

**App 专属支付**（携程包车）：只跳「请在 App 内完成支付」，换方式也无码；核「待支付」后把单号金额发本人去 App 付，30 分钟不付自动释放。

## 「做到」的定义

把页面停在**用户只剩一个动作**的状态：

- 该登录的先登到「需要人工那一步」（账号已填、只差密码/验证码）
- 该选的选完（日期、席别、数量、规格、地址）
- 该填的填完：注册／收货／联系／发票／公司资料等非敏感字段一个不留空
- 该进的进到付款页/确认页
- 用户回来后，剩下的操作**不超过 1–2 次点击**

不要交回一个「你自己去看看」的半成品，也不要交回一张空表。

## 填表怎么做

- 资料来源优先级：memory / USER.md 里已有的本人资料 > 浏览器已存自动填充 > 上次同类任务的记录 > 问用户
- 主人在 USER.md 里写了收货人、收货地址、手机号的默认值，就直接用来填，不再问本人
- 能用浏览器自动填充就用（触发 autofill，V 不读取、不记录明文），尤其是证件号一类被列为本人专属的字段
- 地址、电话、邮箱这类字段填完要核对一遍格式（邮编、区号、+86 这些细节最容易错）
- 填完自查：页面上还有没有空格？有 → 继续填，不要发卡片

## 遇到阻碍先自解

报错、定位失败、页面变了、点了没反应 → 换手段，不要第一下就交回。

定位优先级（从稳到脆）：
1. **a11y-tree / role + name**（`computer` 的 `get_accessibility_tree`、Playwright 的 getByRole）
2. **DOM selector**（稳定 id / 语义属性）
3. **视觉坐标**（最后手段，仅当上面都读不到；浏览器自身 UI，如密码 autofill 下拉，只能走这一层）

操作方式：
- 点击走**原生 click**，不要 JS `.click()`（Ctrip／Porkbun 实测不吃）
- 输入走**真实键盘**，不要直接 set value（重渲染会清空，实测）
- 桌面聊天框输入多行任务时，先聚焦目标应用输入框，使用工具支持的 `mode="insert_text"` 一次插入全文；核对目标、正文和停止条件完整后，单独点击发送按钮，避免换行被当作提前提交。
- 发送后核对完整消息已进入目标对话且输入框无残留；收到 ACK 只证明接单，不能替代正文完整性或执行结果验收。窗口移动、缩放或焦点变化后，重新截图定位再提交，不复用旧坐标或向不明焦点发送快捷键。
- 读状态优先 `evaluate` 读 DOM / console / network；截图只做视觉确认
- 截图超时 → 改用 snapshot / a11y tree

等待与重试：
- 断言式等待：元素存在 / 可见 / 可点 / 文本出现，不要固定 sleep
- 重试要有上限和退避；**同一手段连续两轮不通才升级**（换手段或发卡片）
- 每一步一次可验证断言；失败必须说清卡在哪一步，不盲重试

## 接管卡片（五要素）

停下来时只发这五件事，不让用户自己找位置：

1. **已经做到哪**（登录到哪、选好什么、填好什么）
2. **现在停在哪一页**（站点 + 页面 + 链接）
3. **你要做的那一件事**（输密码 / 过一个验证码 / 确认付款 / 补实名 / 点提交）
4. **做完回到哪一步**（「回来说一声就行」/ 点哪个按钮）
5. **预计还剩几步**

首选 `desktop_handoff_request`（用户直接接管 V 的浏览器，上下文不丢）。不可用时给链接 + 上述五要素文字。

## 用户做完之后

默认**继续接手跑完**——提交、取证（订单号/截图）、核验结果、必要时取消或退订。不再停下问「要继续吗」。

只有出现新的本人专属动作（又一次付款、又一次硬件 2FA）才再次发卡片。

## 边界（不变，限制的是手段不是次数）

- 不绕验证码 / 不绕风控 / 不绕反爬；「新设备验证」这类风控邮件不代确认
- 不经手密码与卡号，不读取、不记录、不代填
- 邮箱验证码只用于本次任务，读到即用，不留存
- 实名证件号只在本人手上出现；能用浏览器自动填充就自动填充，不能就交本人
- **协议可代接受**：办理 主人已授权的任务时，可以阅读并代为接受完成任务所需的服务条款、隐私政策、软件许可或使用协议，不因“接受协议”本身再次索要确认。先核对关键条件；接受不扩大原任务授权，涉及新增购买、付款、订阅或其他超出任务范围的承诺时，仍按该事项的授权范围处理。接受后核验页面状态并继续执行，不把协议许可当成已完成业务。
- 不扩大授权范围（如提权、改配置、开常驻进程）——先提案再执行

授权分级（越往下越要拦）：
- **L0 只读** —— 自动
- **L1 页面内操作** —— 自动
- **L2 提交 / 不可逆**（下单、退订、建号、发布）—— 执行 + 事后报备
- **L3 身份 / 资金**（密码、硬件 2FA、支付密码 / 卡号、实名）—— 永远 handoff，不硬试；扫码付款按「付款怎么做」走

## 密码与凭据（别踩的三个坑）

- **受保护凭据用 `browser_fill_secret` 填网页**：用 `secrets list` 核对 `LOGIN_` 条目及允许域名；已有条目直接代填。snapshot 取 ref，沿用 profile、targetId；密码与确认框填两次时，第一次用 `keep:true`，第二次按后续登录需要决定是否保留。以 `filled:true` 验收，不读回密码；实际出现人机验证再交接。
- **不在聊天里收密码**：飞书消息会进 session transcript，等于落盘。要落密码走掩码输入或一对一私聊（REDLINES 的 Credential Red Lines）
- **最省事的路**：让浏览器自己生成并保存强密码，V 以后只触发 autofill，全程不接触明文
- **长私钥（PEM）不走掩码卡片或云文档**，用公钥或文件附件

## 常见失败模式

| 现象 | 处理 |
|---|---|
| 到登录/注册就停 | 先查 profile——大概率跑在空 profile 上 |
| 按钮点击无效 | 换原生 click；仍无效 → a11y 定位 + 真实鼠标事件 |
| 输入框被清空 | 改真实键盘逐字输入 |
| 截图超时 | 改 snapshot / a11y tree，截图只做视觉确认 |
| 页面重渲染导致定位失效 | 每次操作前重新定位，不复用旧坐标 |
| 连续两轮同一手段失败 | 停下，换手段或发卡片，说清卡点 |
| 出现 hCaptcha / Turnstile / 滑块 / 图形题 | 不解、不重试、不让人选方案，直接 `desktop_handoff_request` 交接，过完之后 V 接着做 |
| 表单字段缺资料 | 先查 memory / USER.md / 浏览器自动填充，别直接把人叫回来 |
| 卡在收邮箱验证码 | 自己开收件箱取；风控类验证邮件才停手 |
| 发了登录 / 付款二维码就停下等回复 | 同一轮里短间隔盯页面，过期就刷新重发 |
| 任务全自动完成 | 直接汇报结果 + 证据，不要多问一句 |

## 验证清单（交回前自检）

- [ ] 用的是有资料的那条 profile（不是空 profile）
- [ ] 页面停在「用户只剩一个动作」的状态
- [ ] 所有非敏感字段（含注册信息）已填完，页面上没有空表
- [ ] 五要素齐了，用户不需要自己找位置
- [ ] 没有经手密码 / 卡号 / 硬件 2FA 明文；邮箱验证码没进聊天

## macOS 文稿访问恢复验收

遇到 Keynote 多版本并存或文稿访问拒绝时：
1. 按明确应用路径选择目标版本，并核对实际 bundle ID、版本与解析路径；后续自动化调用使用同一身份，不靠应用显示名推断版本。
2. 在目标应用内通过「文件 → 打开」明确选取文稿，验证系统文件选取路径；远程选取无法可靠完成时，只交给本人这一个动作，不扩大目录权限或绕过 sandbox。
3. 本人打开成功后，重新验证自动打开、原生读取和新导出；核对源版本未变、导出时间及完整页号覆盖（含 skipped 页），不以旧缓存判定恢复。只以“不保存”关闭任务自己打开的文稿，保留本人文稿。
4. 新的原生自动访问通过后，仅解除已验证恢复的访问延期，保留无关失败、处理中锁与完成状态；把“访问恢复”和“整文件分析写入完成”分别验收。
