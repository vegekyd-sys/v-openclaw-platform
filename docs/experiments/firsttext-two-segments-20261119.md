# 生产 V /vds 首字两段拆分（2026-11-19）

只读分析，V 上没有改动、没有发消息、没有重启。机制实验在 VLab 上直连 DeepSeek API。脚本在 `lab/firsttext-split/`。

## 结论

首字口径：飞书 create_time → 第一段正文推送。11/16–11/19 /vds 共 2,986 条（排除同会话上一轮未结束的消息），p50 约 13 s。

1. **模型段（开跑→首字）不是一个整体，分两类回合。**
   - 62% 的回合「直接回答」，开跑→首字 p50 5.8 s。这 5.8 s 能用一条线性式解释（R²=0.86）：**固定约 1.8 s + 每 100 万输入 token 2.0 s + 每 1000 推理 token 5.7 s**。按中位数（输入 44 万、推理 416 token）是 1.8 + 0.9 + 2.4 s。本地准备（Gateway 0.16 s，app-server 0.1 s）可以忽略；DeepSeek 前缀缓存命中 p50 99%，不是瓶颈。
   - 38% 的回合「先调工具再说话」，开跑→首字 p50 24 s。其中三分之二是多轮模型请求（p50 2 轮，p90 11 轮），三分之一是工具执行，主要是 shell 命令。
   - **>30 s 的长尾里，93%（179/192）是先调工具的回合。**用户在这类回合里 12.7 s 就能看到工具进度（首次可见），只是正文要等到 32.7 s。
2. **入场段（发出→开跑）逐日变慢，来自夜班负载，不是会话库变大或 Gateway 自身退化。**夜班每小时少于 30 个回合时，分发→开跑 p50 四天都是 1.03–1.17 s。逐日上涨有两个来源：落在夜班高负载时段（每小时 100 个回合以上）的聊天消息从 16% 涨到 50–54%；高负载时段内的 p50 也从 1.47 s 涨到 2.56–2.71 s（夜班约 11/16 切到 /vds）。Gateway 停顿反而在减少：liveness 告警由每小时 10–15 次降到 0–8 次。spawn broker 和 Workboard 索引（#625/#627）11/19 21:40 才生效，这份数据还没有覆盖到它们。
3. **入场段的长尾（>15 s，占 3.6%）：**约 30 条是视频消息，开跑前会同步跑 `makaron-cli analyze` 做视频理解，分发→开跑 p50 39 s，6 次以 ExecaError 失败。约 19 条撞上 Gateway 停顿，2 条撞上重启，其余还没归因。

## 数据与口径

- `[firsttext-e2e.1]`：V journal，11/16 00:00 – 11/19 23:30 共 4,021 条，其中 /vds 3,035 条。同一会话上一条记录的 endAt 晚于本条 sentAt 时记为排队，共 33 条，单列。
- 模型段明细：trajectory 里的 `session.started` / `prompt.submitted` 给出 threadId 和 turnId，再对 Codex rollout 的 `task_started`、UserMessage、每次请求的 `token_usage_record`、推理/消息/工具完成时间。11/18 15:18 之前的运行在 trajectory 里查不到（2,132 条），所以模型段明细样本是 11/18 15:18 – 11/19 23:30 的 878 个 /vds 回合，覆盖 90 个线程，rollout 共 538 MB。
- 用 rollout 核对过流式：正文第一个 token 在推理项完成后 p50 40 ms 内到达，长回答也一样。所以 Gateway 记的首字就是「推理结束」，正文没有被缓冲。

## 段二：发出→开跑

| 子段 | 低负载 p50 / p90 | 高负载 p50 / p90 |
|---|---|---|
| 飞书 create_time → Gateway 收到 | 0.86 / 1.35 s | 0.88 / 1.72 s |
| 收到 → 分发 | 0.01 / 0.94 s | 0.25 / 1.53 s |
| 分发 → 开跑 | 1.08 / 2.55 s | 2.29 / 6.88 s |

低负载指当小时夜班 Codex 回合少于 30 个，高负载指 100 个以上；回合数取自 journal 的 `codex-turn-tail` 行。

按天、按负载分桶（分发→开跑 p50，括号里是当天消息落在该负载档的占比）：

| 日期 | <30 | 30–99 | ≥100 |
|---|---|---|---|
| 11-16 | 1.07 s（37%） | 1.33 s（47%） | 1.47 s（16%） |
| 11-17 | 1.10 s（19%） | 1.25 s（28%） | 1.97 s（53%） |
| 11-18 | 1.03 s（39%） | 2.54 s（11%） | 2.71 s（50%） |
| 11-19 | 1.17 s（15%） | 1.96 s（31%） | 2.56 s（54%） |

- 低负载那一列不随日期变，所以会话库、状态库增长不是原因。agent 库现在 46 GB。
- 结论和 11/18 并发研究一致：夜班 /vds 回合每次开始约 1 s、每次工具调用约 0.33 s 的 Gateway 主线程开销，挤占了聊天的入场。修复（spawn broker、Workboard 索引）今晚刚上 V，**明天要用同样的分桶验收**：高负载档 p50 应从约 2.5 s 降向 1.3 s。脚本是 `load.py`。
- 低负载下仍有约 1.08 s，几乎全在「分发→显示输入中」（p50 1.06 s）。这段里具体做了什么，现有埋点拆不开。要拆的话需要在分发和 runStart 之间补阶段时间戳：会话解析、路由、lane 排队、agent-command、codex prepare。
- 收到→分发是双峰的（0.01 s 或约 0.25 s），群消息更常落在慢的一侧。带图片的消息这一段 p50 是 1.3 s（下载），分发→开跑还要多约 1 s。

## 段一：开跑→首字

### 直接回答的回合（545 个，62%）

用户消息到首字（user→tok）按推理 token 与输入大小分桶，取 p50：

| 推理 token \ 输入 | <25 万 | 25–45 万 | 45–65 万 | >65 万 |
|---|---|---|---|---|
| <300 | 2.47 s | 3.19 s | 3.45 s | 4.46 s |
| 300–700 | 4.77 s | 4.83 s | 5.47 s | 5.56 s |
| ≥700 | — | 8.74 s | 10.52 s | 9.12 s |

- 推理 token 是最大的变量：<200 时约 3 s，800–1,600 时约 9 s，≥1,600 时约 16 s。推理 token p50 416，p90 超过 1,000。实测解码约 5.5 ms/token。
- 上下文大小是第二个变量：每 100 万输入 token 约 2 s。聊天会话的输入 p50 是 44 万 token，65 万以上占四分之一。
- 缓存命中 p50 99.2%，99% 以上和 97–99% 两档没有差别。新线程第一轮命中 64%，一共 48 个回合，量很小。
- 空闲时长：30 分钟内续用线程 p50 5.3–5.9 s；空闲超过 30 分钟后 7.1 s，多出来的是 resume 时注入的 developer 消息（app-server 准备从 0.1 s 变成 0.5 s）。
- 回合内压缩只有 5 次，在出字前的 4 次。这几天不是因素。

### 先调工具的回合（333 个，38%）

- 开跑→首字 p50 25.0 s，p90 105.6 s。首字前的时间里，模型请求占 67%（p50 19.4 s），工具执行占 33%（p50 4.2 s）。首字前请求次数 p50 2、p90 11。
- 首字前调的工具：CommandExecution 1,497 次，远多于其他；view_image 59 次，message 30 次。
- 只有 60 个回合在调工具前发过 commentary。有 commentary 的回合首字明显早，例如 3.5 s 发出 commentary、4.3 s 首字。

### 直连 DeepSeek 的机制实验（VLab，不经过 Gateway 和 Codex）

- **推理档位**：`reasoning.effort` 设 low、medium、high，推理 token 一样（68–369，三条提示各跑一次，没有规律），说明服务端不区分这三档。`effort: none` 推理 token 为 0，首字 0.29–0.62 s（同样的提示设 high 时 0.66–1.72 s）。`thinking: {type: disabled}` 在 Responses API 上不起作用。旧记忆里写的「Codex 设 none 关不掉推理」是 Codex 0.152 时的结论，0.169 下要重新验证。
- **缓存前缀大小**：前缀 15.6 万 / 46.8 万 / 93.6 万 token、缓存命中、`effort: none` 时，首字约 1.3 / 2.4 / 4.5 s。响应头到达时间随请求体大小线性增长（0.75 / 2.25 / 4.5 MB，对应 0.8–1.0 / 1.6–2.1 / 3.0–4.1 s），说明大部分成本是上传整份上下文再在服务端过一遍。DeepSeek 不接受 gzip 请求体（返回 400）。V 的上行比 VLab 快：V 上 45–65 万 token 的请求，响应头 p50 1.27 s，20 万以下 0.55 s。

## 长尾（首字 >30 s，占 22%）

- 192 条里 179 条是先调工具的回合：模型一轮一轮推理加跑命令，不是排队，也不是卡顿。
- 其余 13 条直接回答的回合里，5 条推理 1,100–4,400 token（单这一项就 13–30 s），8 条是入场等待 18–54 s（下面这类）。
- 入场等待超过 15 s 的 108 条：视频约 30 条（视频理解同步阻塞，p50 39 s）、图片 10 条、Gateway 停顿 19 条、重启 2 条，其余约 40 条没有找到对应日志，疑似同会话 lane 上有其他工作。

## 改法（按对首字中位数的收益排序）

下面的模拟基于 11/18 15:18 – 11/19 的 877 个回合，基线首字 p50 14.2 s、p90 62 s、>30 s 占 22%。

| # | 改法 | 预计效果（模拟） | 风险与代价 | 验证状态 |
|---|---|---|---|---|
| 1 | 先调工具的回合，先用一句话告诉用户要做什么（Codex commentary），再调工具 | p50 14.2→11.1 s，p90 62→21 s，>30 s 22%→3% | 只改提示（V 的 AGENTS.md 或 developer instructions）。群里话会变多；DeepSeek 不一定稳定遵守。正文口径会变：这句话本身就是正文 | 未做。需要 VLab candidate 确认三点：DeepSeek 在 Codex 里会照做；飞书卡片把它当正文推送；不影响后续工具调用 |
| 2 | 聊天回合关掉推理（`effort: none`），或者只对短消息关 | p50 14.2→10.6 s，p90 62→51 s | 回答质量和工具调用的可靠性会变差，这是最大的风险。可以只对短消息或纯对话关，但需要判定规则 | 机制已在 API 层验证（none 时推理为 0）。还没验证 Codex 0.169 能否把 none 传下去，也没做质量评估 |
| 3 | 夜班负载下的入场段：spawn broker + Workboard 索引（已上 V） | 高负载档分发→开跑 p50 约 2.5→1.3 s（按 VLab A/B 推算），整体首字 p50 约 −0.5～−1 s | 已上线 | 明天白天按 `load.py` 的分桶验收 |
| 4 | 缩小每轮上下文：降低 DeepSeek 线程的自动压缩上限（例如 30 万），配合回合后压缩 | 输入一律压到 20 万时：p50 −0.9 s，p90 −3 s。先调工具的回合每轮请求都省 | 压缩更频繁，每次冷算 70–80 万 token，耗时 16–22 s，也有费用；长对话会丢细节。#598（回合后压缩）当时关掉了没上线 | 未做。如果要做，先在 VLab 测质量和压缩频率 |
| 5 | 视频消息不同步阻塞：先开跑并回一句「在看视频」，视频理解改成工具或后台任务 | 视频消息首字约 54 s→约 15 s（占消息 1.2%） | 产品决定：现在的分镜分析提示是有意配的。失败（ExecaError）时白等最多 60 s | 未做 |
| 6 | 低负载下分发→开跑那约 1.08 s | 未知 | 要先补埋点 | 需要在分发→runStart 之间加阶段时间戳（候选 + 下一次重启） |

不值得做的：DeepSeek 缓存命中（已经 99%）、Gateway 和 app-server 的本地准备（合计约 0.3 s）、首字→推送（0.7 s，主要是建卡和推送的网络往返）。
