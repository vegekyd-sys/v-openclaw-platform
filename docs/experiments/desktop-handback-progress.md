# 电脑交还后的统一进度展示

接管页点击「交还给 V」后，桌面插件会认领交还事件并调用原生 agent RPC 续跑。此前这个入口没有绑定统一进度展示，原群可能直到最终结果才看到回复，无法判断是否已经开始处理。

本次在独立 worktree `codex/desktop-handback-progress` 开发。桌面插件在原有运行准入之前，以同一个幂等键绑定 `desktop-handback` 展示任务；排队、公开进度、工具状态、最终结果和原生投递回执都使用已有统一机制。没有新增执行器、轮询模型或第二条结果发送链路。

## 行为边界

- 交还服务的 origin 校验和原子 claim 保持不变。同一交还时间的重复调用使用相同 run ID，下一次交还获得新 ID。
- 只有会话已有有效飞书外部投递绑定时才创建进度卡；归档、重置、其他渠道、已有原生展示归属或管理器不可用时保持原执行行为。
- 展示绑定在执行准入之前完成，首条进度不会因建卡异步完成而丢失。续跑尚在排队时显示排队状态；准入成功不等于任务完成。
- 使用续跑自身的生命周期，不订阅整个会话的背景任务结束摘要，避免旧任务完成状态覆盖仍在执行的电脑交还任务。
- 明确拒绝准入时展示失败；外层 30 秒等待超时不伪装为执行失败。最终结果投递重试不重新执行模型。
- 公开进度和工具状态可以展示，私有推理不会进入卡片。

## 验证

本地相关回归 107/107 通过，覆盖运行绑定、首次进度、工具事件、结果去重、重复交还、排队状态、会话隔离、重置失效、失败提示、投递重试、原生 ACK、补丁重建及平台测试登记。

真实候选验证使用私有 Gateway、实际桌面插件轮询、原生 `runtime.subagent.run` / agent RPC 和模型。桌面交还服务及飞书 API 使用本地模拟端点；不向真实群发送消息，不改动共享实例。候选通过：一次交还认领、7 个结果前进度快照、1 张最终结果卡，原生 ACK 成功，重复轮询未增加任务或消息。候选内部测试约 97 秒，全链路约 177 秒，`sharedUnchanged=true`。使用 Codex / VDS DeepSeek；结果与文件哈希见[脱敏证据](desktop-handback-progress-evidence.json)。

准备候选时修正了三个测试环境问题：旧测试脚手架注入了当前版本已移除的配置项、测试额外设置了未在插件 schema 中声明的轮询间隔、隔离插件缺少依赖解析路径。最终候选使用默认轮询间隔和私有 runtime 的现有依赖；这些调整均仅在本次测试脚本中。

## 发布组合

`lab/build-desktop-handback-progress.mjs` 从已捕获的当前发布生成飞书管理器和 monitor 的精确字节，输出发布计划及 SHA-256。桌面插件的 `index.js` 和新增 `core/task-presentation.js` 位于独立的 `/opt/v-desktop-handoff/plugin` 部署目录，另外列入 manifest；仅部署飞书计划不能完成本修复。

后续获得合入、部署授权时，需要把这两个插件文件与飞书产物一起纳入受控发布并核对原文件，最后在共享 VLab 验证实际接管页交还、忙时排队、原群进度和终态。候选通过不代表真实接管页、真实飞书群或生产验收；本 PR 阶段不合入 dev，不部署共享 VLab 或生产。
