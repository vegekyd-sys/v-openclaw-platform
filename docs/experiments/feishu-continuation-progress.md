## 根因与补丁

`current` cron 用原群作为来源和结果投递目标，实际执行仍进入独立的 `agent:…:cron:…:run:…` 会话。原有展示只覆盖人类消息、排队请求、跨会话消息、子任务回报和语音任务，没有为 cron 执行创建展示归属；独立会话本身也没有可用的飞书外部绑定。最终投递正常，不代表过程已经可见。

候选在 cron 完成准入及投递解析后，用来源会话的 session ID、生命周期版本、账号、目标及话题进行精确校验。受理时显示自动续接锚点，执行器实际进入时启动原生卡；该次运行 ID 和独立执行会话的公开进度事件更新同一张卡。原始提示词、拼接历史、推理、工具参数和工具输出均不进入展示。

最终结果在原有 cron 结果归档、静默判断、目标校验及内容转换之后，交给这张原生卡投递。真实消息 ACK 才标记成功。失败保留原卡和原结果重试，已有发送权时不切换另一发送器；不重跑模型。消息工具已确认发送、静默、取消和超时各有对应收尾。Gateway 重启时，尚未经过最终投递判断的模型原始输出不会被直接补发。

每轮续接独立持有卡片，新的人类对话和其他续接不会结束它。续接卡不附加原有单槽的全会话后台汇总行，避免其他任务结束时把仍运行的续接标为“后台任务已结束”；普通人类对话、跨会话和语音卡保留原汇总行为。未来尚未开始的定时任务不会冒充正在运行。本补丁不改变调度时间、业务修复逻辑、collector 的超时或并发策略。

## 第二轮：重启后的原生子任务续接（2026-10-27）

17:09 的子任务回报锚点和 17:14 的追问都没有过程卡，不能由“展示记录 phase=running”推断它们已经执行。继续核对数据库后，正在写入原会话的是重启前的另一条任务：`activeWriterRunId`、`lifecycleRunId` 均为 `announce:codex-native:01a17819-73bf-7981-be18-4195d8c7f4fd:01a17c60-44a6-70f0-886c-10d9a28dc8e9:succeeded`，本轮 `startedAt=17:09:40`。对应展示记录 `a26f31f5…` 已在 16:53 重启时被标记为失败且已投递。17:09 新回报和 17:14 追问的运行编号不同，仍在同一会话队列里等待。

根因是执行恢复与展示恢复的状态不一致：展示管理器 `recover()` 在没有执行终态时直接 `finish(restartError)`，持久化 `delivered=true` 并移除运行绑定；核心随后以原 run ID 恢复执行，展示层仍把它当作已结束。现场 17:19 的 `progress_card` 成功只证明计划存储更新，不证明飞书已展示。原生 GPT 路径不是整体缺少展示入口；先前仅凭空快照推测事件绑定丢失不足以定位本例。

对照运行捕获的生产展示代码可确定复现：启动恢复后的记录为 `phase=failed, delivered=true`，且 `runs.has(sameRunId)=false`。第二轮修复：

- 无终态的重启只发布“等待原任务恢复或核对”的中断状态，不创建执行失败，不确认最终投递，也不自行重跑工作。
- 真正进入执行器的同一运行重新校验会话、生命周期及外部投递绑定，接管原卡。仅兼容旧版本生成的精确重启错误；真正成功、失败或取消的终态不能因此重开。
- 旧的重启通知回执不算恢复后的结果回执，保留原卡和锚点，等真实最终 ACK 后再确认完成。
- 新子任务回报和追问显示排队状态；模型选择不等于开始执行，实际准入后才切为处理状态。排队、子任务续接和 cron 卡不使用全会话的“后台任务已结束”汇总。
- 原生执行回调没有附带 run ID 时，使用已验证执行上下文补齐；显式不同运行或会话的事件仍被拒绝。
