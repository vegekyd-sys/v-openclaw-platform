# 飞书回复建议方案 · 第二版：放在聊天框外面

日期：2026-10-28。状态：**方案待 Tianyi 拍板，未写产品代码**。分支 `claude/reply-suggestions-design`。

**和第一版的区别**：第一版把建议做成回复卡片底部的按钮，Tianyi 否了：

> 主要的并不是在聊天框里面的展现。这个展现不出来的，而是看一下飞书机器人有没有一些案例，怎么展现出那个 suggestion 啊……就是这个内容不是一个聊天框里的内容

这一版重做「放在哪、怎么展示、点了以后怎么发」。**生成部分（§2 的评测）保留**，第一版的展示调研和实测挪到附录 A。

目标不变：V 每次回复完，给用户 2–3 条他接下来可能想说的话，点一下就发出去。要求「简洁但是有见解，可以真实的帮助用户」。worker、`/vcodex`、`/vds`、`/vcc` 都要能用。需要拍板的事在 §7。

## 1. 结论先说

| 问题 | 推荐 |
|---|---|
| 飞书自己怎么做 | 飞书官方智能伙伴把「结合对话内容推荐你可能想问的问题」做成**回复下方的悬浮气泡**，输入框正上方还有常驻的「新话题 / 选择场景」；在群里从右上角「⋯」打开**右侧侧边栏**和它对话。这些是官方 AI 的专属界面，**开放平台没有给第三方机器人的接口**（§3） |
| 第三方能用的位置 | 能做到「不进消息流、按会话动态变化」的，只有 H5 类位置：**会话标签页**、**桌面端侧边栏**、**输入框「+」菜单**、**消息快捷操作**；外加左侧消息列表里的**应用消息流卡片**。机器人悬浮菜单、群菜单、斜杠命令都是后台静态配置的（§3.2） |
| 放在哪 | 和 Recap 共用一个**「V」面板**（H5）：上半部分「接下来可以说」，下半部分回顾。入口：会话顶部标签页「V」（手机、桌面都有），桌面端从群菜单 / 私聊悬浮菜单 / 「+」菜单 / 在 V 的回复上「⋯ → 让 V 给建议」打开，在**聊天右侧侧边栏**里和聊天同屏（§4） |
| 点了以后 | 面板用飞书 H5 免登拿到**点击者本人的用户令牌**（申请 `im:message.send_as_user`），服务端以**用户本人身份**把这句话发进会话。会话里就是一条他自己发的普通消息，走正常入站，**痕迹问题自然解决**（第一版原生回调的做法群里看不出是谁说的，见附录 A） |
| 怎么生成 | 不变：另调一次 DeepSeek v4 flash（思考 low）。58 条 V 真实对话、两位评委盲评，2 分（「会直接点」）建议占 66%（不开思考 41%），与「主模型 + 全上下文」打平（§2） |
| 首字延迟 | 零影响。面板打开时按需生成；侧边栏开着时，每轮回复收尾后再生成并推给面板 |
| 成本 | 只有面板打开或开着时才生成，最多也就是每条回复一次：约 0.0013 美元一次，V 全量回复也只有每天约 0.8 美元 |

### 2.1 候选方案

短上下文：本轮用户的话（1000 字内）、V 的回复（3000 字内，掐头去尾）、本轮用过的工具名、最近 2 轮对话各截 300 / 500 字。全上下文：最近 4 轮、本轮全部工具调用参数和工具结果摘录。

### 2.2 评测集与方法

- **数据**：近 6 天有活动的 22 个飞书会话（群聊 17、私聊 5；worker 12、`/vcodex` 6、`/vds` 4），每个会话取截至 2026-10-28 01:25 最近 3 个「用户发言 → V 有正文回复」的回合，去掉 `NO_REPLY` 后共 58 条。这段时间没有活跃的 `/vcc` 会话，所以**评测集里没有 claude-cli**；它和其他 runtime 走同一个 dispatcher，实现阶段补测。数据从 V 的会话库只读导出，只留在本机临时目录，**不进 git**。
- **人工标注**：46 条「应该出」，12 条「应该不出」。后者包括：测速 / 定时任务回执、卡片 JSON、定时推送混进来的日报、「构建已触发，正在跟踪」「我去看一下」这类任务还在跑的回复、对话已收尾。
- **评委**：每条样本把各方案的建议打乱、匿名后一起给评委，逐条打 0/1/2 分（2 = 具体有见解、用户很可能直接点；1 = 相关但平淡；0 = 空话 / 泛泛 / 对不上 / 重复 V 已做的事 / 编造），再给每组整体 1–5 分并选最佳组。主评委是 Grok 4.7（参评方案里没有 xAI 的模型，避免自评偏好）；第二评委是 GPT‑5.6，用来看一致性。两位评委选出的最佳组有 33/46 一致。
- **生成和评审都在 V 上跑**，用 V 自己的 DeepSeek / Azure / xAI 通道，所以延迟接近生产。脚本在 [`experiments/reply-suggestions-eval/`](../experiments/reply-suggestions-eval/)。

### 2.4 读这些数字的结论

1. **思考是关键，模型大小和上下文多少不是。** 不开思考的 flash 最常犯的错是「重复 V 已经做完或说过的事」（Grok 标了 20 条「重复」），在 prompt 里专门强调（A3）也没用；开思考以后同类错误降到 8 条。
2. **独立调用 ≈ 主模型顺带。** worker / `/vds` 会话上 A2 与 B 打平（72% vs 72%）。`/vcodex` 会话上 B 的 0 分更少，差距来自上下文，不来自 GPT（见拆分实验）。所以第一期用短上下文，把**本轮工具调用的名字和关键参数**也喂进去（飞书 dispatcher 里拿得到），作为向 C2 靠拢的便宜做法。
3. **朴素 prompt 不能用。** A0 的建议几乎都是「XX 具体怎么做？预计多久？」这种长问句，46 条里只有 6 条能通过 20 字的长度过滤。

好的建议大多是三类：**在 V 给的选项里替用户做选择**、**指出没核实的前提或风险**、**把下一步说成一句可执行的指令**。这也是 prompt 里要求的优先级。

### 2.6 为什么不让主模型在回复末尾顺带产出

1. **质量没有优势。** 见 §2.3，独立调用已经打平。
2. **要改四套 harness。** worker 的系统提示、Codex 的 developer instructions、claude-cli 的附加系统提示各改一处，还要在流式输出里把建议那段剥掉。流式卡是边生成边推送的，剥晚了标记文字会在卡片上闪一下。
3. **动缓存前缀。** 改系统提示会让所有会话的提示缓存失效一次；以后调 prompt 每次都要再失效一次。
4. **拖慢卡片收尾。** 建议写在正文后面，卡片要多等 50–500 个 token 才能收尾，用户看到「生成中」的时间变长。
5. **会干扰正文。** 主模型知道自己要写建议，正文里容易少写一步，留给建议去问。

独立调用把这些都避开了：只改飞书 dispatcher 一处，prompt 可以随时调，失败了也不影响正文。

### 2.7 Prompt、过滤和「不出」的规则

**Prompt**（全文见 [`prompts.py`](../experiments/reply-suggestions-eval/prompts.py) 的 `DESIGNED`）：替用户想 2–3 句下一步最值得对 V 说的话；必须锚定本轮的具体对象；优先「选择 / 风险前提 / 关键追问 / 具体下一步」；不超过 18 个汉字；禁止空话、泛泛、重复 V 已说的、编造用户私有信息、主动建议不可逆操作（除非 V 正在等拍板）；想不出 2 条好的就输出 `skip`。

**过滤**（[`filt.py`](../experiments/reply-suggestions-eval/filt.py)）：去掉空话（好的 / 继续 / 谢谢 / 收到…）、泛泛（详细说说 / 还有吗 / 举个例子…）、超过 20 字宽的、两两字面重复度 ≥ 50% 的；剩不到 2 条就整组不出。A2 的输出几乎不触发过滤，过滤是兜底。

**什么时候不出**，按顺序：

1. **结构规则**（代码里直接知道，不用模型）：
   - 只给「对用户入站消息的回复」出建议。定时任务结果、心跳、提醒推送、会话间转发、语音通话转写，这些都不出。
   - 最新一条回复不是正文（例如工具自己发的卡片、纯媒体、`NO_REPLY`、空卡被收回）不出。
   - 会话还有后台任务在跑（回复卡上的「后台任务」行 `v_bg_tasks` 还在进行中），不出。等后台任务的完成回复出来再出。
   - 用户在建议生成期间又发了新消息，丢弃这次结果。
2. **文字规则**（[`gate.py`](../experiments/reply-suggestions-eval/gate.py)）：回复开头 160 字内出现「正在跟踪 / 已触发 / 稍后汇报 / 我去查 / 我先核对…」这类说法，且回复不到 600 字，判定为「任务还在跑」，不出。
3. **模型自己判断**：prompt 里列了纯通知、对不上、对话已收尾、想不出好建议这几种情况，输出 `skip`。

评测集上：12 条应该不出的，前两层规则全部拦住；46 条应该出的，前两层没有误拦，模型自己又跳过了 4 条（A2）。**注意文字规则是在这 58 条上调出来的，有过拟合的风险**，上线后要记录每次命中了哪条规则、用户点没点，用真实数据再调。

### 2.8 首字延迟与 Gateway 安全

- 首字口径按 memory `firsttext-measure-what-user-sees`：飞书发送 → 卡片推出第一段正文。建议不进消息流以后，生成有两个时机，都**不碰首字，也不推迟正文收尾**：①面板打开时按需生成；②面板开着的时候，每轮回复在 `performStreamingClose` 收尾后再生成一次推给面板（见 §4.3）。
- 生成是一次异步 HTTP 请求，Gateway 主线程只做拼 prompt 和解析几百字节的 JSON。不读会话库：最近 2 轮对话由 dispatcher 在内存里按会话留一个小环形缓冲（每个会话 2 条，每条截断），Gateway 重启后第一轮就只用本轮内容。这条是专门针对 V 历史上「整读会话卡主线程」的事故（memory `gateway-full-session-reads-gc-stall` 等）。
- 超时 12 s，失败或超时就不出，不重试，不影响正文。

**结论**：飞书把「建议」做在消息流外面、紧贴输入框，这正是 Tianyi 想要的形态；但这块界面只开放给官方 AI。第三方机器人要做同样的事，只能用开放给第三方的 H5 位置去「拼」出来：桌面端用侧边栏贴在聊天右侧，手机端用会话标签页。

### 3.2 聊天框外能放内容的位置（只列和「建议」相关的结论）

Recap 方案（PR #504 §3）已经把每个位置的权限、手机 / 桌面样式查过一遍，这里不重复，只补「放建议」角度的判断，以及我这边新查的三个位置（标有 ★）。

## 4. 推荐方案：和 Recap 共用的「V」面板

### 4.1 入口与形态

```text
手机：会话顶部标签「V」 ─────────────► 全屏 V 面板
桌面：会话顶部标签「V」 ─────────────► 会话内嵌 V 面板
      群菜单「💡 V」/ 私聊悬浮菜单「💡 建议」/ 输入框「+」→ V
                          ─────────────► 聊天右侧侧边栏里的 V 面板（和聊天同屏，可一直开着）
      在 V 的某条回复上「⋯ → 让 V 给建议」
                          ─────────────► 侧边栏，针对这条回复的建议
```

面板从上到下：

1. **接下来可以说**：2–3 条建议，整行按钮，每条一行。下面一行小字「针对 V 14:32 的回复」，让人知道它对应哪一条。
2. 「✏️ 改一改再发」：把选中的建议放进面板里的输入框，改完再发（飞书不支持往聊天输入框里预填，只能在面板里改）。
3. **回顾**（Recap 那部分，结构见 PR #504 §5）。

手机宽度的静态样例：[`docs/experiments/reply-suggestions-panel/v-panel-mock.html`](experiments/reply-suggestions-panel/v-panel-mock.html)，截图 `v-panel-mock-手机.png`（样式沿用 Recap 的回顾页样例；内容是虚构的 CDN 选型场景）。

### 4.2 点了以后：以用户本人身份发出

- 面板打开时用飞书 H5 免登（`requestAccess`）拿到查看者身份。第一次点建议时，再增量申请 `im:message.send_as_user`，用户在飞书里点一次同意；服务端换到这个人的用户令牌（刷新令牌 7 天，常用就会续上）。
- 点建议 → 面板调 V 的后端 → 服务端以**用户本人身份**调发消息接口，把这句话作为普通文本发进对应会话。会话里就是他自己发的一条消息：别人看得到是谁说的，V 走 `im.message.receive_v1` 正常入站，流式卡、过程流、steer 一切照常。V 的群配置是 `requireMention=false`，群里也不需要 @V。
- 发出后：手机端面板自动关闭回到聊天（或调 `enterChat` 跳回）；桌面侧边栏保留，建议区变成「已发送：…，等 V 回复」。
- **没授权的人**（例如外部成员、拒绝授权的人）：退回第一版实测过的原生 `k:"quick"` 路径，以点击者身份合成入站，同时面板提示「这条是代你发给 V 的，群里不会显示你的消息」。也可以选择对没授权的人干脆不提供点击发送，只能复制。见 §7 第 3 条。
- 不用 `sendMessageCard`：它只能发卡片，而且文档没写清以谁的身份发。

### 4.3 什么时候生成、怎么刷新

- **面板打开时**按需生成：取这个会话最近一条 V 回复（以及它对应的用户消息、本轮工具名、前 2 轮），按 §2 的方法生成，按「会话 + 最近回复的消息 id」缓存。打开面板时如果缓存命中，就立刻显示。
- **侧边栏开着时**：每轮 V 回复在 `performStreamingClose` 收尾后，Gateway 发一个「这个会话有新回复」的事件，面板收到后去拉新建议（3–4 s 后出现）。这样桌面上就接近官方智能伙伴的体验：聊天在左边，建议在右边跟着变。
- 没人开面板就不生成，不花钱。
- 「什么时候不出」的规则（§2.7）照用：面板上显示「这轮 V 还在跑，等它说完再给建议」或「这条是通知，没有建议」，而不是空白。

### 4.4 跨 runtime 与群聊

- **四种 runtime 共用一套。** 建议只依赖 Gateway 手上的入站消息、最终正文和工具事件，不进任何 harness。读历史时不用 `chat.history`（`/vcc` 会话会走 CLI 导入分支整读），用 dispatcher 在内存里留的最近 2 轮；没有时用 Recap 也在用的有界尾部读取 `readSessionTranscriptBoundedMessageTailPage`。
- **群聊谁能点**：面板是每个人自己看的，谁打开就以谁的身份发。建议是按「最近一条 V 回复的提问人」的口吻写的，所以群里给非提问人看时，在建议上方加一行「这是针对 XX 的问题」，见 §7 第 4 条。
- **私聊**只有一个人，没有这个问题。

### 4.5 和 Recap 的分工

- **一个标签页「V」、一个 H5 面板**，回复建议在上，回顾在下。标签页的安装和修复复用 #495 的 `v-feishu-phone-tabs`（Recap 方案里已经计划把它泛化成「V 标签页管理」）。
- **身份与发送**共用一套：H5 免登、成员校验、以用户身份发消息。Recap 的「继续」按钮就是「以用户身份发一句话」，和建议的点击是同一个后端接口。
- 生成各自独立：回顾是按需整理一段对话，建议是针对最近一条回复；两者都用 DeepSeek flash 旁路调用，共用限流（全局并发、同会话单飞）。
- 第一版里约定的「回复卡页脚」和 `card.action.trigger` 钩子都不需要了。只有「未授权用户退回原生 quick」这一条还会用到原生回调，不需要新补丁。

### A.1 实测：原生 quick 回调的点击路径

2026-10-28 02:01，在 `/vcodex` 测试群点了样例卡 ① 上的「群里谁点都行会不会乱」。V 生产日志：

```
02:01:36.754  handling structured card action v.reply_suggestion from ou_cb133fd4…   ← 点击回调
02:01:37.107  received message from ou_cb133fd4… in oc_260a9450… (group)              ← 以 Tianyi 身份入站
02:01:37.112  message in group oc_260a9450…: 群里谁点都行会不会乱
02:01:47.539  Closed streaming: cardId=7701409353592851491                              ← /vcodex 正常流式回复
02:01:47.570  dispatch complete (queuedFinal=true, replies=1)
```

说明：

- 点击到入站 0.35 s，之后与手打消息走同一条 `handleFeishuMessage` 路径：会话记录里是 Tianyi 说的话，流式卡、过程流、steer 都照常。卡片按钮用的是 OpenClaw 已有的 `ocf1` / `k:"quick"` 信封，**这一步不需要改任何代码**。
- 群里看不到 Tianyi 的消息气泡。V 的回复作为被点卡片的回复出现（卡片下方显示「1 条回复」），回复内容是对「群里谁点都行会不会乱」的回答，但旁人看不出这句话是谁说的。这就是 ① 必须补「卡片原地更新」的原因。
- 飞书重投同一次回调时，OpenClaw 按回调 token 去重；但用户连点两下、或者点了两个不同按钮，每次都是新 token，会入站两次。所以回调里要记录「这张卡已经点过」，更新后的卡片把按钮全部置灰。

### A.2 当时设想的卡片样式（已放弃）

```
┌────────────────────────────────────────┐
│ V 的回复正文（流式）                      │
│ ☑️ 后台任务行（已有，若有）                │
│ 接下来可以说                    （灰色小字）│
│ [ 56%到90%，修窗口够吗           ]         │
│ [ 先把9项复核结论发我过目         ]         │
│ [ 水盒和接水盘，定个统一判据      ]         │
│ ──────────────────────────────────────── │
│ Agent: V × Makaron | Model … | Runtime …  │  ← 现有页脚
└────────────────────────────────────────┘
点击后：被点的那条高亮，其余置灰，下面加一行灰字
「↳ 蔡天懿 发送了「先把9项复核结论发我过目」」
```

- **竖排整行按钮**：建议多是 10–18 个字，横排三个放不下就会换行，手机上更乱；竖排在桌面和手机上都稳定。
- 只有最新一张回复卡的按钮有效。点了旧卡片上的按钮，如果会话已经往前走了，回调回一个 toast「对话已经往前走了，这条建议过期了」，不发消息。这样也避免了在 V 正在跑的时候把旧建议 steer 进当前回合。
- 卡片的 `summary`（会话列表里的预览文字）不变，还是正文开头，不把建议放进预览。


第一版结论在聊天框外的方案里仍然有用的两点：①原生 `k:"quick"` 回调能以点击者身份进入正常入站（未授权用户的退路）；②它不会在群里留下「谁说的」痕迹，所以第二版改为以用户本人身份发送。
