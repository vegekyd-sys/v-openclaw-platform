# 跨会话传话验证（2026-10-07，VLab candidate）

被验对象：原生 `sessions_send` + 两个回移 9.8 的 dist 补丁（`sessions-send-reply-once`、`mcp-after-tool-call`）+ 插件 `apps/v-session-relay`。运行方式覆盖 worker（DeepSeek）、vds（Codex + DeepSeek）、vcc（Claude Code）。vcodex 未在 candidate 跑：复制来的 ChatGPT 刷新令牌会连带 V 的登录，留到共享 VLab 用 `vlab.mjs test` 补。不测 Gateway 重启。

## 第一部分：UI 承接 sessions_send 的内容

真飞书：owner 的 VLab 私聊 +「VLab 发布验收 B」群，卡片用飞书接口读回逐条比对。

| 项目 | worker | vds | vcc |
|---|---|---|---|
| 当场答：两边各一张卡、内容逐条一致、无多余消息 | 通过 | 通过 | 通过 |
| 异步（对方 60–75 秒）：卡片进行中→已完成，核心唤醒发起方，结论只发一次 | 通过 | 通过 | 通过（claude-cli 按自身规则拒跑 75 秒 sleep，内容是"跑不了"，卡片与唤醒正常） |
| 对方正忙：排在当前轮之后处理，卡片正常 | 通过 | — | — |
| 对方失败（无凭据）：两边卡片「中断」并带原因，不误唤醒 | 通过 | — | — |

过程中修掉：claude-cli 的工具结果插件看不到（回移 9.8 的 MCP after_tool_call）；失败的传话被当工具报错跳过；卡片标题不居中、群名 10 字就截断。

## 第二部分：派活（每次实验一个独立 agent，避免共享记忆串味）

W1 派活后用结果写周报；W2 同时派两组再汇总；W3 长任务（对方跑 90 秒）；W4 对方按自己规矩卡住、要发起方确认；W5 对同一会话再派一次（返工）。

| | 正式组（插件提示词开） | 对照组（提示词关） |
|---|---|---|
| W1 ×3 | 9/9 | 9/9 |
| W2 | 3/3 | 3/3 |
| W3 | 3/3 | 3/3 |
| W4 | 3/3，三次都出现"设计组质疑色值来源→发起方确认→出稿" | 未跑 |
| W5 | 3/3，接着自己上次的分析往下做 | 3/3（vds 一次判分误判：编号写成 ②⑤⑧） |
| 发出的 sessions_send | 29 次，全部当场等回复 | 21 次，全部当场等回复 |
| 对方试图再转发被拦 | 0 | 2 |

结论：

1. 派活、拿结果接着干、多轮来回，靠的是原生 `sessions_send` 和 V 自己的能力；插件提示词关掉也一样完成。插件提示词可测的作用只有一项：让对方不去再转发（0 次 vs 2 次）。
2. 50 次派活 V 全部选择当场等（最长 157 秒），所以 30 秒丢回信的问题在这些实验里没被触发。核心补丁的价值在对方做得比 V 愿意等的更久、或 V 明确不等的时候（单独的 75 秒异步测试已验证）。
3. 我们新增的、原生没有的是：飞书里看得见（第一部分）、长任务回信不丢、防兜圈。
4. 生产上 V 的所有群和私聊共享同一份记忆：第一版实验里不同场次互相读到了对方的代号。这本身是一条跨群信息通道。
5. candidate 的 makaron 工作区是 172KB 空壳，被唤醒轮自称"还没有名字"大概率是这个原因；上 V 前在共享 VLab 真实工作区复核。
