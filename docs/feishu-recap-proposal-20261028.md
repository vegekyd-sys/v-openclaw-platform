# 飞书 Recap（会话回顾）方案 · 第二版：放在聊天框外面

日期：2026-10-28。状态：**方案待 Tianyi 拍板，未写产品代码**。分支 `claude/feishu-recap-design`。

**和第一版的区别**：第一版把回顾做成聊天流里的一张卡片（命令或菜单触发），Tianyi 否了：

> 主要的并不是在聊天框里面的展现……recap 也是，就是这个内容不是一个聊天框里的内容。

这一版重做「放在哪、怎么展示」，生成侧（只读有界尾部、旁路模型、缓存）保留，见 §6–§7。第一版的卡片样例留在 [`experiments/feishu-recap-samples/`](experiments/feishu-recap-samples/)，只作为字段结构参考，不再作为展示形态。

## 1. 结论

| 问题 | 推荐 |
|---|---|
| 放在哪 | **主位置：每个会话顶部的「V 回顾」会话标签页**（`chat_tabs` 的 url 类型）。它和「消息」「文件」两个标签并列，点开就是一个 H5 回顾页，**不进消息流**。#495 已经在私聊里装过同类标签「📞 打给 V」，安装、修复、身份认证这一整条链路可以复用。**辅助入口**：桌面端从群菜单或私聊机器人菜单点「📋 回顾」，同一个页面会在**聊天右侧的侧边栏**打开，和聊天同屏（电话页现在就是这样打开的）。**主动提醒**（第二期）：会话里出现「需要你」的事项时，用**应用消息流卡片**在左侧消息列表里放一条「V · 某会话：等你选 CDN」，也不进聊天框 |
| 怎么展示 | 回顾页结构从上到下：一句话现状 → 需要你 → 进展 → V 接下来 → 风险 → 时间线，底部是「继续」和「刷新」。打开页面时才按需生成；会话没有新消息就直接用缓存。手机端打开是一个全屏页，桌面端在标签页或侧边栏里打开 |
| 生成和成本 | 保持第一版的设计：转录有界尾部（80 条、160 KB）加上结构化状态，交给 `deepseek/deepseek-flash` 做旁路补全，按转录水位缓存；不碰任何整读路径。所以这里**只在有人打开页面时才花钱**，不在每轮回复后预生成 |
| 跨 runtime | Recap 读 OpenClaw 自己的转录，不碰该会话的 runtime，worker、`/vcodex`、`/vds`、`/vcc` 一套代码通用（`/vcc` 的完整性待实测，见 §7.3） |

## 4. 推荐组合

```text
                    ┌───────────── 被动：用户自己去看 ─────────────┐
私聊：顶部标签「V 回顾」 ── 点 ──► H5 回顾页（手机全屏 / 桌面在标签页内）
      机器人菜单「📋 回顾」 ─ 点 ──► 同一页面（桌面在侧边栏）
群聊：顶部标签「V 回顾」 ── 点 ──► 同一页面
      群菜单「📋 回顾」 ──── 点 ──► 同一页面（桌面在侧边栏，和聊天同屏）
                    └───────────────────────────────────────────┘
第二期 主动：应用消息流卡片「V · <会话名>：需要你 …」── 点 ──► 同一页面
```

- 所有入口都指向**同一个回顾页**，页面由 URL 里的会话标识决定显示哪个会话。
- **标签页的安装**：照搬 #495 的 `ensurePhoneTab`。在 `bot_p2p_chat_entered` 或 `bot.added` 时检查、补齐、修复标签页，已经在的就不重复建，写之前先读，写之后再读回确认。电话和回顾两个标签页可以由同一个处理器一起管理。
- **H5 页面**：放在 Voice 服务（`openclaw.tianyi.live`）旁边，或者共用它的身份交换。打开页面时，先用飞书 JSSDK 免登拿到查看者身份，服务端再核对「查看者是这个会话的成员」，然后向 Gateway 请求回顾。拿不到身份时，只显示「请在飞书里打开」，**不显示内容**。
- **和「回复建议」共用页面**：建议也是「聊天框外」的内容。和回复建议 session（PR #505）已对齐成一个标签页「V」：**建议在上、回顾在下**。理由是建议只有三行，手机首屏不用滚动就能看到；回顾比较长，往下翻即可。标签页由本方案泛化后的 `v-feishu-phone-tabs.mjs` 统一管理，入口（标签页、菜单、侧边栏）也只做一套。
- **共用的发送接口**：「继续」和「点建议」走同一个页面后端接口 `POST send {chat, text, source: "suggestion" | "recap-continue", suggestionId?}`。先核对成员关系，再用**查看者本人的用户令牌**（H5 免登时增量申请 `im:message.send_as_user`）调 `im/v1/messages` 发一条普通文本：群里能看到是谁说的，V 也通过 `receive_v1` 正常入站。不经 Gateway RPC 注入（`chat.send` 一类在飞书里看不到，旁人只看到 V 的回复）。拿不到令牌时返回 `needs_consent`，由页面拉起授权；用户拒绝授权就退回合成入站，并在页面上提示「群里不会显示你的消息」。限流两边共用：全局并发 2，同一会话单飞。

## 5. 回顾页怎么展示

### 5.1 结构（手机竖屏优先）

1. **标题区**：会话名，「截至 14:32 · 基于最近 42 条消息」，右上角有刷新按钮。
2. **一句话现状**（大字，60 字以内）。
3. **需要你**（只有在有内容时才出现，放在最上面，带强调色但不用绿色）：未回答的 ask_user、待批审批，以及模型判断出的待决定事项，最多 3 条。在群里，**只把属于当前查看者的事项高亮**，其他人的事项写成「天懿：确认…」。
4. **进展**：▶️ 进行中、☑️ 已完成（灰色），最多 6 条。
5. **V 接下来**：最多 3 条。
6. **风险**：只写有具体依据的风险，最多 2 条，橙色。
7. **时间线**（默认折叠）：最近几段对话的一行式摘要，带时间，相当于第一版卡片里的「更早的事」。
8. **底部按钮**：「继续」：通过共用的发送接口（§4），以查看者本人身份往会话里发一句「按回顾继续：<下一步>」，发出前弹出确认框，可以编辑。「回到聊天」：applink 跳回这个会话。

页面视觉沿用 Tianyi 一贯的偏好：少线少框，不用绿色，靠字重和灰度分层。静态样例页在 [`experiments/feishu-recap-samples/recap-page-mock.html`](experiments/feishu-recap-samples/recap-page-mock.html)，390×844 手机宽度的截图 `recap-page-mock-mobile-20261028.png` 放在共享笔记目录里。

### 5.2 长度、刷新与过期

- **模型输出**是固定结构的 JSON，每个字段都有字数上限，由代码校验后渲染。渲染时做 HTML 转义，转录里的文本不能注入页面。
- **打开页面时**：转录水位没变就直接用缓存，并显示「x 分钟前生成」。水位变了就先显示旧内容，标「有新消息，正在更新…」，生成完再替换。手动刷新也走同一条规则。
- **会话被 `/new` 或 `/reset`** 以后，页面显示新会话的回顾，旧会话不再显示。
- **没有定时任务**，也不在每轮回复后生成。唯一的例外是第二期的消息流卡片：「需要你」这一项直接取自结构化状态（ask_user、审批），**不需要调模型**，只有这些状态变化时才更新卡片。

### 5.3 群聊和私聊的区别

| | 私聊 | 群聊 |
|---|---|---|
| 谁能打开 | 本人 | 群成员（服务端按身份核对成员关系） |
| 内容范围 | 这个私聊会话的全部内容，包括工具进展 | **只总结本群**，工具原始输出脱敏，不混入任何其他会话 |
| 「需要你」 | 全部 | 只高亮查看者自己的事项 |
| 「继续」按钮 | 有 | 待定。因为是以查看者本人身份发出、群里看得到是谁说的，可以放；如果查看者没授权、只能走合成入站，群里看不到这句话，就不显示这个按钮 |
| 第二期消息流卡片 | 发给本人 | 只发给「需要你」事项的那个人 |

## 6. 生成方式（沿用第一版）

### 6.1 读什么

1. **转录有界尾部**：`readSessionTranscriptBoundedMessageTailPage`（9.1 core 已有）。先读每条消息的 `serialized_bytes` 元数据，再按字节预算挑选正文，大的 base64 行在读正文之前就被跳过。参数：`maxMessages=80`、`maxBytes=160 KB`。只保留 user 和 assistant 的文本，工具只留名字和一行结果。
2. **起点**：取「这个人上次看回顾时的水位」和「最近一段 4 小时以上空闲之后」中更晚的那个。窗口里如果有压缩摘要，就作为背景放在最前面。
3. **结构化状态**（按会话点查）：`progressCard.get` 的工作清单、未回答的 ask_user、待批审批、后台任务数。

**不用**：`chat.history`（`/vcc` 会话的 CLI 导入分支会 `mode:"full"` 整读）、`SessionManager.open`、`openModelContext`、`sessions.list`。转录投影不是最新时（`SessionTranscriptProjectionUnavailableError`）不等、也不触发重建：有缓存就给缓存，没有就提示稍后再试。

### 6.2 模型

用 `deepseek/deepseek-flash`，走 9.1 core 原生的旁路补全（`simple-completion-runtime` 或 session observer 用的 `runIsolatedCompletion`）。这条路径不建会话、不写转录、不开工具、不占该会话的 lane。模型显式指定，**不设置 `agents.defaults.utilityModel`**，否则会顺带启用上游的 session observer 和 Side chat，每个 run 都去 patch session entry。5xx 由回顾自己重试一次，再失败就换 `openai/gpt-6-luna`。转录只当引用数据，里面的指令一律不执行。

### 6.3 缓存

缓存键是 (agentId, sessionKey, sessionId, 转录水位, 查看范围)。存在 Gateway 内存 LRU（512 条），另外每个会话落一个 0600 的小 JSON 到 state 目录。**不写 session entry**。

## 7. 成本与 Gateway 安全

### 7.1 约束

| 历史事故 | 回顾怎么避开 |
|---|---|
| 整读 session 表 | 按 sessionKey 点查，不列会话 |
| 同步整读大会话 | 只读有界尾部，在读正文之前就按字节过滤 |
| 投影脏了整段重建 | 投影不是最新就放弃 |
| 定时全量扫描 | 没有定时任务；只在页面打开时生成 |
| fan-out 饿死交互流量 | 全局最多 2 个生成并发，同一会话单飞，每人每分钟最多 6 次 |
| 同 appId 第二条长连接 | 不开新连接。H5 后端通过 Gateway RPC（actor 准入）请求回顾；标签页安装复用现有 dispatcher 的事件 |

### 7.2 上线门槛

在 candidate 上用 VLab 快照里的一个 V 级别大会话（≥100 MB，含 base64 大行），连续做 20 次回顾、并发 2。标准：每次新增的主线程占用 p95 ≤ 50 ms，没有超过 200 ms 的停顿可以归到回顾上。

### 7.3 四个 runtime 的实测

worker、`/vcodex`、`/vds`、`/vcc` 各开一个会话聊 3 轮，再分别生成回顾，核对内容。`/vcc` 要特别确认 OpenClaw 转录里有没有最终回复。如果没有，就补读 Claude CLI jsonl 的末尾，倒读、封顶 160 KB。

## 8. 实现路径（拍板后）

1. **`v-session-recap.mjs`**（Gateway 进程内）：有界读取、状态汇总、补全、校验、缓存。提供 Gateway RPC `v.recap.get`，带 actor 准入：调用方必须提供经过核验的飞书身份，并且是该会话的成员。
2. **回顾页**：一个静态 H5，加上 Voice 服务里一个后端路由，负责核验身份、调用 `v.recap.get` 和渲染页面。身份交换复用 #495 / Voice PR #166 的 SDK 流程。
3. **标签页和菜单**：`v-feishu-phone-tabs.mjs` 泛化成「V 标签页管理」，同时管电话和回顾（名字、URL、修复规则共用一套）。群菜单加「📋 回顾」，`pc_url` 设成侧边栏打开。私聊机器人菜单加一项跳转链接，这一步要发布应用版本，属于外部配置，需要 Tianyi 确认。
4. **第二期**：应用消息流卡片（主动的「需要你」）。权限开通、应用版本发布都要单独确认。
5. **测试**：
   - 单元测试：字数上限、转义、身份和成员关系拒绝路径、标签页幂等。
   - candidate：主线程门槛和四个 runtime。
   - 真人：用专用测试机器人「V - Candidate 测试」（`cli_aa4ad84139385bcf`）验标签页、侧边栏、菜单，手机和桌面都截图。不在 V 或 V - Lab 应用上开第二条长连接。
6. **交付**：报告分支、commit 和结果；合 dev、上 V 由 Tianyi 决定；重启由 Monitor 排进 `v-self-restart`。

**主要风险**：H5 免登对外部账号可能不通（#495 记录过 SDK 2700002，至今没定位）。如果外部成员也必须能看，就用 doc 类型标签页兜底（§3 第二行）。代价是只能定时改写文档、持续花模型费用，而且文档里放不了按钮。
