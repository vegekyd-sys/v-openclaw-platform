# 飞书 Recap（会话回顾）方案

日期：2026-10-28。状态：**方案待 Tianyi 拍板，未写产品代码**。分支 `claude/feishu-recap-design`。

目标：像 Claude Code CLI 的 recap 一样，把某个会话最近聊了什么、做到哪了、下一步要注意什么，压成一张卡片显示在飞书里。worker、`/vcodex`、`/vds`、`/vcc` 四种 runtime 都要能用，而且不能拖慢 Gateway 主线程。

最后一节列出需要拍板的六件事。

## 1. 结论先说

| 问题 | 推荐 |
|---|---|
| 放在哪 | 第一期做三个**被动入口**：① 文字命令 `/recap`（私聊、群聊都能用，零后台配置）；② 私聊机器人菜单「📋 回顾」（推送事件）；③ 现有快捷面板（quick-actions）里加一个「回顾」按钮。第二期可选一个**主动入口**：私聊里隔了很久再进来时，自动推一张回顾卡（默认关闭，按人开启）。群公告、群置顶、工作台、应用主页、每张回复卡的页脚按钮都不做 |
| 怎么展示 | 一张独立的 JSON 2.0 卡片，从上到下是：一句话现状、进展、需要你、V 接下来、风险提醒、折叠的「更早的事」、按钮。正文控制在 500 字以内。群里默认用「仅你可见」的临时卡片，点「发到群里」才公开 |
| 怎么生成 | 按需生成，用会话转录的**有界尾部**（只读最近 80 条、最多 160 KB），加上进度清单、待回答问题这些结构化状态，交给 `deepseek/deepseek-flash` 做一次旁路补全（不进会话、不开工具、不写转录）。按转录水位缓存：会话没有新消息，就直接复用上次的结果 |
| 成本 | 不调用 `chat.history`、`SessionManager.open`、`sessions.list`，任何整读都不碰；读取是逐条字节封顶的点查。全局最多 2 个生成并发，同一会话同一时间只生成一个。上线前在 candidate 上用 V 规模的大会话量主线程占用，p95 不超过 50 ms 才算过 |
| 跨 runtime | Recap 读的是 OpenClaw 自己的转录。四种 runtime 的回合都落在这里，生成也不碰该会话的 runtime（不开 Codex 线程，不起 claude-cli 进程），所以一套代码通用。`/vcc` 的尾部是否完整需要在 candidate 里实测（见 §6.3） |

### 群聊里「仅你可见」

飞书有一个临时卡片接口 `POST /open-apis/ephemeral/v1/send`，在群里只发给指定的人看：

- 只能在群聊里用，不能转发，只在对方在线的客户端上显示。
- 机器人要在群里。

群里有人点了回顾，默认发给他一个人看，不打扰其他人。卡片上的「发到群里」按钮会把它换成一张普通卡片，公开发到群里。这个接口能不能带 JSON 2.0 按钮、点了以后能不能原地更新，都要实测。如果不行，就退回成直接在群里发普通卡片，卡片上写明「天懿 请求的回顾」。

## 4. 卡片怎么展示

### 4.1 信息结构（从上到下）

1. **标题栏**：「回顾」或「群回顾」，副标题写范围和时间（「私聊 · 截至 14:32」或「最近 24 小时 · 4 人参与」）。群里加「仅你可见」标签。
2. **一句话现状**（加粗，60 字以内）：在做什么，现在卡在哪一步。
3. **进展**：最多 4 条。☑️ 已完成的用灰字，▶️ 进行中的用正常颜色。更早完成的放进最后的折叠区，最多 3 条。
4. **需要你**：只放必须由人决定或提供的东西，最多 2 条，没有就整段不显示。这一段优先采用结构化来源（未回答的 ask_user 问题、待批的审批），模型的判断只用来补充。
5. **V 接下来**：V 准备做的事，最多 3 条。
6. **⚠️ 风险**：只放有具体依据的风险（截止时间、额度、失败过的步骤），最多 2 条，橙字。没有就不显示。不写泛泛的提醒。
7. **按钮**：私聊是「继续 / 刷新」，群里是「发到群里 / 刷新」。
8. **页脚**（灰色小字）：依据的范围（多少条消息、时间窗），生成于几分钟前，以及「不会写进对话记录」。

### 4.2 长度控制

- 模型只输出固定结构的 JSON，每个字段有字数上限，由代码校验后再渲染成卡片。模型不直接写 markdown，这样既避免格式漂移，也避免被转录里的文本注入。
- 卡片可见正文控制在 500 字以内，卡片 JSON 不超过 20 KB（飞书单卡上限是 30 KB）。
- 超出部分不截半句，直接丢弃低优先级的条目。顺序是：先丢更早的事，再丢已完成的进展，最后丢风险。

### 4.3 刷新与过期

- **缓存键**：(agentId, canonical sessionKey, sessionId, 转录水位 maxSeq, 可见范围)。点「刷新」时如果水位没变，直接复用缓存，只更新卡片上的「x 分钟前」，不再调模型。
- **卡片不自动跟着会话更新**。自动更新会在每条新消息上产生写入和卡片 PATCH 风暴，所以只在点刷新时更新。
- **会话被 `/new` 或 `/reset`**（sessionId 变了）：旧卡片上的按钮会提示「会话已重置，这张回顾已过期」，并把卡片改成灰色。
- **飞书只允许修改 14 天内发出的卡片**。超过 14 天的回顾卡，点刷新时改成发一张新卡。
- **缓存放在 Gateway 进程内存里**（LRU，最多 512 条），再落一个小 JSON 文件到 state 目录，权限 0600，按会话分文件。**不写 session entry**：写 session_nodes 会把 entry_json 撑大，后续的整读都会更贵。

### 4.4 群聊和私聊的区别

| | 私聊 | 群聊 |
|---|---|---|
| 谁能触发 | 本人 | 群里任何人（沿用该群的发言准入） |
| 默认谁看得到 | 本人 | 只有触发的人（临时卡片），点「发到群里」才公开 |
| 内容范围 | 这个私聊会话，包括工具进展、后台任务 | **只总结本群会话**。不带工具原始输出，用原生的 `redactToolPayloadText` 脱敏，绝不混入其他会话或私聊的内容 |
| 人称 | 「你 / V」 | 待办按人名列（「天懿：确认…」）。不发真正的 @，避免回顾卡触发提醒 |
| 继续按钮 | 有。以点击者身份往会话里发一句「按回顾继续：<下一步>」 | 不放。群里替人发一句话容易让人困惑，改放「发到群里」 |
| 自动推送 | 第二期可选 | 不做 |

## 5. 生成方式

### 5.1 读什么

按下面的顺序拼输入，总量封顶（转录 160 KB 加上结构化状态约 8 KB，大约 1.5 万 token）：

1. **转录的有界尾部**：用 `readSessionTranscriptBoundedMessageTailPage`（9.1 core 已有，`session-accessor` 里）。它先读每条消息的 `serialized_bytes` 元数据，再按字节预算挑选要读的正文，所以 5–19 MB 的 base64 大行在读正文之前就被跳过了。参数：`maxMessages=80`、`maxBytes=160 KB`、`offset=0`。读出来以后只保留 user 和 assistant 的文本；工具调用只留工具名和一行结果，图片换成「[图片]」。
2. **起点**：以「上次给这个人生成回顾时的水位」和「最近一段 4 小时以上的空闲之后」两者中**更晚**的那个为准。都不存在时，就取上面那个尾部窗口。如果窗口正好跨过一次压缩，就把压缩摘要作为「更早背景」放在最前面（它本来就在可见尾部里）。
3. **结构化状态**，都是按会话的点查，很便宜：当前进度清单（`progressCard.get`，即飞书卡片上那份工作清单）、未回答的 ask_user 问题、待批的审批、后台任务数（`v_bg_tasks`）。「需要你」和「进行中」优先从这里取。

**明确不用的**：`chat.history`（`/vcc` 会话在合并 Claude CLI 记录时会走 `readSessionMessagesAsync(mode:"full")` 整读，见 `chat-D3QlhTHk.js` 的 `readChatHistoryPage`）、`SessionManager.open`（fenced 整读）、`openModelContext`、`sessions.list`。

**转录投影不是最新的时候**：`withCurrentProjectionSnapshot` 会抛出 `SessionTranscriptProjectionUnavailableError`，并在后台启动一次 reconcile（现在已经挪到 worker 线程）。这时回顾不等它、也不触发重建，有缓存就先给缓存，没有就提示「记录正在整理，稍后点刷新」。

### 5.2 用哪个模型

**`deepseek/deepseek-flash`**：它是 V 的默认主模型，中文好、便宜，首字也快。走 9.1 core 原生的旁路补全接口：`simple-completion-runtime` 里的 `prepareSimpleCompletionModelForAgent` 加 `completeWithPreparedSimpleCompletionModel`，或者 session observer 用的 `runIsolatedCompletion`。会话标题生成器和 Side chat 也建在这同一套接口上。具体用哪一个，在 candidate 里看哪个的准备开销小再定。这条路径：

- 不建会话，不写转录，不开工具，不经过 vlab-worker，也不占该会话的 lane。
- 模型直接显式指定。**不去改 `agents.defaults.utilityModel`**：一旦设了它，上游的 session observer 和 Side chat 会在每个 run 上自动跑起来，还会 patch session entry，这是另一笔写入负担。

**失败处理**：已知 5xx 不会触发 OpenClaw 的 fallback（见 memory `upstream-5xx-never-triggers-fallback`），所以由回顾自己重试一次。还失败就换 `openai/gpt-6-luna`（V 配置里的备用模型）。都失败时，卡片显示「这次没生成出来」和「重试」按钮，不写占位的假内容。

**提示词约束**：转录被当作引用数据，里面的任何指令都不执行（沿用 Side chat 的 private-reference 包裹方式）。只能根据转录里有的内容写，不知道就省略。输出必须是严格 JSON，按 schema 校验，不合格就重试一次。

### 5.3 什么时候生成

**按需生成**，不在空闲时为所有会话预生成。原因是预生成需要先找出「哪些会话变冷了」，这又是一次扫会话表，正是 V 反复踩过的坑（workboard 巡检、sessions.list 全量）。而且 V 每天活跃的会话里，绝大多数没人会去看回顾。

唯一的预热场景是第二期的私聊自动推送：`bot_p2p_chat_entered` 一到就开始生成，大约 3–5 秒后发卡。这时用户刚打开聊天，正好看到。

**延迟预期**：读取在 50 ms 以内，flash 生成 2–5 秒。菜单和按钮会先回一个 toast「正在整理回顾…」。普通卡片先发一张只有标题加「整理中…」的卡，生成完再原地更新。临时卡片如果不能更新，就等生成完再发。

## 6. 成本与 Gateway 安全

### 6.1 设计约束（对照 V 的历史事故）

| 历史事故 | 回顾怎么避开 |
|---|---|
| 整读 session 表（`loadGatewaySessionLookupStoreUncached` 148 MB，PR #462/#468 才修好） | 按 sessionKey 点查 entry（走已修好的 exact 路径），绝不列会话 |
| 同步整读大会话（36–158 MB，每 MB 10–12 ms） | 只读有界尾部，在读正文之前就按字节预算过滤掉大行 |
| 投影脏了整段重建 | 投影不是最新就放弃，不触发重建 |
| workboard 每分钟全量扫描 | 不做任何定时扫描，只在有人点或打开私聊时才动 |
| fan-out 批次饿死交互流量 | 全局最多 2 个生成并发，同一会话单飞，每人每分钟最多 6 次，等待队列上限 32，超出直接回「稍后再试」 |
| 飞书回调超时被重投 | 回调立即应答，后台异步处理（照搬 phone-tabs 的「先 ack 再排队」） |
| 同 appId 再开一条长连接会抢事件 | 不开新连接，全部挂在 Gateway 现有的飞书 dispatcher 上，出站只调 REST |

### 6.2 上线门槛（candidate 实测，不达标不提交）

- 用 VLab 数据库快照，挑一个 V 级别的大会话（≥100 MB、含 base64 大行），连续做 20 次回顾、并发 2。期间用 `perf_hooks` 记录事件循环延迟，再用 inspector 抓 profile。标准：**每次回顾新增的主线程占用 p95 ≤ 50 ms，没有超过 200 ms 的停顿可以归到回顾上**。
- 单次读取的耗时、读了多少字节、多少条，都写进 receipt 和日志（`v-recap read bytes=… msgs=… ms=…`，日志里不带会话内容）。
- 预备方案：如果补全的模型准备（`prepareSimpleCompletionModelForAgent`）本身就占主线程很多，就按 agent 缓存已经准备好的模型对象。如果还不够，把生成挪到一个专用的 worker_thread 里做。

### 6.3 四个 runtime 的实测清单（实现阶段）

在 candidate 里，每个 runtime 各开一个会话聊 3 轮，再分别做回顾，核对尾部读取能拿到 user 和 assistant 的文本，并且生成结果确实反映了这 3 轮在聊什么：

- worker（deepseek-flash）
- `/vcodex`（codex）
- `/vds`（codex + DeepSeek）
- `/vcc`（claude-cli）。这一个要特别核对：OpenClaw 转录里有没有最终回复。`chat.history` 对 claude-cli 有一条「CLI 导入」分支，说明本地转录可能缺内容。如果确实缺，就在尾部读取里补读 Claude CLI 会话 jsonl 的**末尾**（从文件尾部按字节倒读，封顶 160 KB），绝不整读

另外两项：同一会话在 `/vds ↔ /vcodex` 之间切换以后做回顾，确认不会触发换线程；回顾以后再发一条消息，确认会话的上下文和首字都不受影响（回顾不写转录）。
