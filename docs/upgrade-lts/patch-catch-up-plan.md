# 9.1 补丁怎样才追得上新版本（2026-10-29）

## 为什么现在越追越远、而且没法验证

1. **补丁的形态是编译产物。** V 上的改动是对 `dist/` 里压缩后 JS 的整文件替换。平台仓库里有 144 个 `lab/patch-*.mjs` 按字符串锚点去改 dist。新版本的文件名、分块、代码形状全都变了，每升一次都要从压缩代码里把意图重新推出来。
2. **源码线在 9/26 停了。** 9/25 那次（fork `versa/main`，见 `versa/PATCHES.md`）已经把当时 V 的 96 个核心文件全部翻成了源码提交，68 个提交里 62 个带单测。之后 V 又发了 81 次版，新增 91 个、改动 32 个核心文件，一个都没进源码线。10/04 定过"新补丁双写"，后来因为目标版本没定暂停了。差距就是从这里开始拉开的。
3. **验证都绑在 9.1 的字节上。** `tests/*.test.mjs`、`lab/*accept*.mjs` 大多直接读 9.1 某个 dist 文件、找某个锚点。换了版本，这些测试本身就失效了。所以只能靠人在 VLab 上点，没法说"新版本上这项补丁还成立"。
4. **跨版本对比混了变量。** 门禁拿"9.1 加全部补丁"对比"新版本加一部分补丁"，结果变好或变差，分不清是版本的原因还是补丁的原因。

## 方案：先在 9.1 上把补丁变成"可 rebase、可测试"的形态，再追

核心想法：**升级的难度不在版本差多少，而在补丁是什么形态。** 9/26 把源码补丁合进 9.6 只用了约一天（三方合并，48,575 个文件里只有补丁相关的 365 个与官方不同），而 dist 补丁每次都要重新推一遍。

### 第 0 步：止血（立刻开始，之后每个 PR 都适用）

- 改 core 或官方插件 dist 的 PR，必须同时带 `versa/main` 上的源码提交，提交要带单测。紧急热修可以先改 dist，24 小时内补源码。
- 平台仓库加一个 CI 检查：`release/captured/` 里新出现或变化的文件，必须能在台账里对上一个源码提交，对不上就红。
- 写补丁前先过一遍三问：
  1. 上游最新版或维护线有没有现成的修复？有就 cherry-pick 上游提交，并在提交信息里注明出处，换线时自动丢掉。
  2. 能不能用插件、钩子或配置解决？
  3. 前两条都不行，才写 V 专属的核心提交。

### 第 1 步：补欠账（约 1 周）

- 把 9/24 之后的 123 个核心文件改动（81 次发版），加上飞书、Codex、钉钉、企微插件上的改动，翻译回 `versa/main` 的源码提交，每个提交带单测。
- 依据都在：每个 PR 的 `lab/release-files/*` 是可读的模块源；10/11 写的 `blame.mjs` 能把每个 dist 改动块归到具体发版。
- 9/25 那次翻 96 个文件用了约两天，这次量级相近。

### 第 2 步：V 改跑 fork 构建的 9.1（约 1 周）

- 从 `versa/main` 整包构建 9.1。
- 在 VLab candidate 上，拿它和 V 现在的字节做对比，**版本相同**：同一套验收、同口径首字和重启时间。因为版本没变，任何差异都只能是翻译错了，**这一步是可以验证的**。
- 通过后，V 改为从 fork 整包发版，dist 补丁和 144 个 `patch-*.mjs` 退役。从此"V 的补丁" = `versa/main` 上的一串源码提交。
- 风险（未验证）：9.1 的源码构建能不能在构建工具链上复现 npm 包。第 2 步一开始先做这个检查。

### 第 3 步：版本无关的验证（约 1–2 周，可与第 1、2 步并行）

两层：

| 层 | 是什么 | 换版本时 |
|---|---|---|
| 源码单测 | 每个提交自带的 vitest 单测（现有 62/68） | rebase 后在新版本上直接跑，哪个补丁的语义坏了当场看到 |
| 黑盒功能契约 | 每个台账编号一条场景，只用 Gateway RPC 或真实飞书（lark-cli），不读任何 dist 文件 | 9.1 上先跑一遍定基线，新版本上跑同一套 |

- 先覆盖"切换当天必须有"的约 60 项：核心、Codex、飞书、语音。
- 现有的验收脚本改写成黑盒；不能黑盒的（纯性能）进门禁脚本。

### 第 4 步：每月一次换线演练（自动化）

- 每出一条新的 extended-stable 月线（约每月中旬），自动把 `versa/main` 的提交栈 rebase 到新线、构建、跑源码单测；然后在演练机上跑黑盒契约和门禁。
- 产出一份"距离报告"，每个提交只有四种结论：
  - 干净
  - 冲突
  - 测试失败
  - 上游已有，可删
- 追赶的工作被摊到每个月，距离始终不超过一条线。报告里的数字是在变小还是变大，一眼就能看到。

### 第 5 步：主动缩栈

- 每月报告里"上游已有"的提交直接删掉。
- 通用缺陷提给上游，被接受一个就少一个。比如整表读取一类、#157935 子会话冻结的修复。这是对外动作，每个 PR 要你批准。
- 能挪成插件的挪出核心。
- 指标：栈里的提交数和改动行数，每个月要下降。

## 真正切到新版本时

- 前四步做完后，切换就是：把提交栈 rebase 到当时维护中的月线，单测和契约全过，门禁过，再按 `promote-to-v` 上线。
- 仍然要解决的是新版本自身的问题：子会话冻结、停机租约、插件源码复制、c15。它们在第 4 步的月度门禁里持续跟踪，不再和"补丁有没有搬全"混在一起。
- V 在第 2 步之前一直跑现在的 9.1 字节，第 2 步之后跑等价的 fork 构建 9.1。**整个过程不需要先升级。**

## 时间

第 0 步立刻开始；第 1–3 步约 3–4 周，期间 V 照常发版（按第 0 步双写）；第 4 步从第一条月线演练开始每月一次。

## 流水线与排期（2026-10-30）

### 怎样证明补上的源码最后真被用上

一份源码提交从写出来到在 V 上跑，中间可能在三个地方丢掉：没进构建所用的分支；进了分支但构建产物里没有；产物里有，但运行时根本走不到。所以检查也分三层：

| 层 | 检查 | 什么算过 |
|---|---|---|
| 血缘 | 构建产物的 `build-info.json` 记着构建所用的提交。台账里每个 `versa:<sha>` 都必须是这个提交的祖先（`git merge-base --is-ancestor`） | 0 个不是祖先 |
| 产物 | **特征串检查**：对每个补丁文件，取 V 字节里新增、原版 9.1 里没有的标识符和文案，逐个到 fork 构建产物里精确查找。找不到的逐条归类：改了名（附新名，并确认新名在产物里）、只在注释里、dist 补丁的锚点机制（源码不需要）、有意不翻（登记原因）、**真缺**。另外做 **C1 逐文件对照**，构建是确定的，所以每处差异都要能解释 | 真缺 = 0 |
| 运行 | 台账每一项一条黑盒契约，并且带**反向对照**：同一条契约在原版 9.1 上必须失败，证明它确实走到了补丁路径，而不是空跑通过 | 契约在 fork 构建上过、在原版 9.1 上不过 |

C5 之后，V 跑的就是 fork 构建，这三层就成了每次发版的回归检查。哨兵再加一项：V 上 dist 的哈希等于发布构建的哈希。

**特征串检查首跑（10/30，汇总分支 `35f7f06f225` 的构建，对照 V 10/30 捕获的 core）**

- 范围：去掉 control-ui 前端资源后，取有意义的标识符和文案。
- 结果：

  | 台账状态 | 文件数 | 特征串 | 构建里能找到 |
  |---|---|---|---|
  | 已标 `versa:` | 146 | 975 | 81.8%（86 个文件全部找到） |
  | `pending`（第二波） | 37 | 618 | 63.6% |

- 抽查了 8 个找不到的：
  - 全部是改了名，或者只出现在注释里（例如 `V_KEEP_RECENT_TOOL_IMAGE_RESULTS` 改成 `KEEP_RECENT_TOOL_IMAGE_RESULTS`，`resolveXaiToolDefaultReasoningEffort` 只出现在注释里，源码里是 `resolveXaiXSearchReasoningEffort`）。
  - 新名都在构建产物里找到了。
- 剩下的 177 个还没逐条归类。归类就是 C1 的工作内容。

### 怎样证明效果一致：归一化代码对照（10/30 Tianyi 拍板采用）

特征串只能说明"代码在产物里"，不能说明"行为一样"。我们有个有利条件：V 线上和 fork 构建都基于 9.1，两边的差别只有"dist 补丁"和"翻译出来的源码"这一处。所以不必用测试去推断行为，可以直接比两边最终运行的代码。

做法（`scripts/normalized-dist-diff.mjs`）：
1. 把 V 的 dist、原版 9.1 的 dist 和 fork 构建的 dist，都交给同一个 esbuild 重新排版，再按顶层函数、类和变量切成块。
2. 只拿 V 相对原版改过的块，去 fork 构建里找对应的块。先按名字找，找不到再按相似度找改了名的。
3. 自动滤掉三类：完全相同；只差格式（压缩后一致：花括号、注释、`300*1e3` 和 `3e5` 这类写法）；只差改名（标识符换成占位符后一致）。
4. 另外列出"只有 fork 改了、V 和原版一样"的块。翻译时顺手做的额外改动就从这里抓。
5. 剩下的每一条，由负责翻译的那队给出四种结论之一：**等价**（写理由）、**有意差异**（写原因，交 Tianyi 过目）、**翻错**（在 fork 上修，带单测，修复前失败、修复后通过）、**工具误报**（写明实际位置）。

|---|---|---|---|---|
| core | 146 | 580 | 161 / 45 / 43 | 255 / 76 / 57 |

**逐条结论（10/30 完成）**

| 队 | 条数 | 等价 | 有意差异 | 翻错 | 工具误报 |
|---|---|---|---|---|---|
| A（记忆、存储、工作板、回合、9/25 M1） | 301 | 169 | 45 | 7 | 80 |
| B（渠道、语音、飞书层、Codex 层；含追加 1 条） | 159 | 80 | 6 | 2 | 71 |

- **翻错 9 条，实际是 6 处漏翻或翻偏。** 每处都在 fork 上修了，带单测，单测在修之前失败、修之后通过，已合入汇总线 `b65dc10193e`：
  - exec 审批的只读快路径（V 不进状态库写事务，fork 每次都进）；
  - 运行中止没传到项目记忆准备；
  - 等待子任务完成投影时，外部中止没被登记；
  - Worker 磁盘巡检每分钟整表读取，而 V 只读活跃行；
  - GPT Live 通话就绪失败时，回给页面的文案多了 "Error: " 前缀；
  - 飞书审批回调把非字符串的 kind/decision 也当成有效值。
- 工具误报主要是两种：同名常量配错了对象；V 的独立模块在 fork 里改了名或被打进别的分块。我在第一版里举过一条"真实差异"：`agent-db-process-coordinator` 默认最长等待，V 300 s、fork 10 s。这条**就是误报**：工具配到了另一个同名常量，fork 里实际也是 300 s。
- B 给工具补了两条重排归一化：`var X = class` 还原成 `class X`，冲突改名的数字后缀折回原名。用新旧两版同输入对比，被新规则滤掉的 15 条逐条确认都只是重排；两处真实翻错在新版下仍然报出。

**有意差异 51 条（交 Tianyi 过目），按性质分组；在 V 的现行配置下，行为都和 V 相同**

| 类别 | 条数 | 内容 |
|---|---|---|
| 诊断埋点、安装锚点没翻 | 25 | `bundlePrepObserver`、`[memory-preparation]`、`OPENCLAW_DB91_PHASE_TRACE` 等计时日志，以及只在安装时按锚点改 dist 的脚本函数。只打日志或在安装时运行，不影响行为 |
| V 里没人启用的代码没翻 | 7 | oc64 快照冲突重试：V 里没有调用方打开 `retrySnapshotConflicts`；回滚阀 `OPENCLAW_V_FULLREAD_HOTPATHS=0`：V 从没设过 |
| fork 比 V 更严 | 8 | 关掉缓存句柄后，按句柄代数重新校验会话 key（`fa88e0faa22`）；cron 策略读取加 `Object.hasOwn`；resume 注册中止时要求有 sessionId；`/model` 限制在飞书以外的渠道只在配置了 owner 时生效（V 配了）；系统 agent 路由把一个可能抛错的调用推迟到真正需要时 |
| 为上游测试或可配置加的开关，默认值与 V 相同 | 10 | 维护冷却可用环境变量覆盖（默认 60 s）；Telegram V Experience 开关默认开；Control UI 只在 RTC 资源存在时注入 import map（发布包里一定存在）；插件加载时的 resolver 改为首次调用时才取；doctor 子进程入口改成当前进程入口（V 上是同一个文件）；内存库的关键词覆盖缓存按连接区分 |
| 结构改法 | 1 | 飞书语音身份由飞书插件通过 plugin-sdk 注册，不再由 core 直接 import 插件路径；超时和报错码相同 |

逐条明细见 `verdicts/team-A.md`、`verdicts/team-B.md`。需要拍板的只有两条，其余都只是知会：
- `/model` 的 owner 条件：V 配了 owner，所以线上行为相同；
- doctor 子进程入口：如果以后换一种入口启动 Gateway，行为会和现在不同。

**第二波起改成"逐字翻"**：第一个提交原样搬 V 的代码，归一化对照必须 0 差异，两边就是同一份代码，等价不需要再证明。想整理代码就另起提交，由单测保证整理前后行为不变。

这样，前面"三层检查"里"产物"那一层的验收，就从"真缺 = 0"收紧为：**每条差异都有结论，翻错 = 0，有意差异经 Tianyi 过目**。黑盒契约和同版本 A/B 退到第二道，只重点验证这些有意差异和高风险模块。

### 固定流程：每份源码都要和 V 对照（10/30 Tianyi 拍板）

在升级分支上，任何 `versa:` 映射都必须带对照结论，CI 门禁会检查（`check-source-map.mjs`）。台账条目没写 `equivalence` 时，CI 会变红。dev 上不要求这一项。每一波源码化都按下面的步骤走：

1. **翻译**：逐字搬 V 的代码，提交到 fork 上并带测试。要整理代码，另起提交，由单测保证整理前后行为不变。
2. **构建**：在汇总分支上构建（固定 `GIT_COMMIT` 和 `OPENCLAW_BUILD_TIMESTAMP`），在 Mac 上用 `nice` 降低优先级，并占用重任务锁。
3. **对照**：`node scripts/normalized-dist-diff.mjs --capture <V 捕获> --stock <原版> --fork <构建> --files <本波文件> --exclude worker --out <目录>`。非 JS 文件逐字节比对，JSON 按内容比对。
4. **沿用旧结论**：`node scripts/normalized-dist-diff-carry.mjs --old <上一轮> --new <这一轮> --verdicts <结论表>`。只有差异文本没变的条目才沿用旧结论，其余列出来重判。
5. **下结论**：剩下的每一条给出四种结论之一。`scripts/normalized-dist-diff-view.mjs` 会去掉排版和改名噪音，只显示语法差异，但它的改名对应来自工具自己的配对，可能配错，所以每条结论都要回到源码核对。翻错的要在 fork 上修，并带一个修复前失败、修复后通过的单测，然后重跑第 3、4 步。
6. **记账**：翻错为 0 后，给台账条目写上 `"equivalence": "normdiff:<构建提交>"`（逐字节相同的写 `identical:<构建提交>`）。新的有意差异写进本节的分组表，交 Tianyi 过目。
7. **合入**：PR 的 CI 要通过 `check-source-map`，合入升级分支 `upgrade/openclaw-lts`。升级分支合入 dev 要等验证完成，并由 Tianyi 明确批准。

逐字翻的文件，第 5 步应该是 0 条待判。如果出现待判条目，说明翻译时动了代码，要么改回去，要么另起提交并在结论里写明理由。
